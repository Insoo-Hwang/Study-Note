# 10. 테스트 · 운영 — 한 페이지 요약

> **테스트는 배포 전에, 관측은 배포 후에 같은 질문을 던진다 — "이게 정말 되는가". 그리고 네 노트를 관통하는 대답은 하나다: 재지 않으면 모른다.**

이 섹션 노트 4개의 핵심만 한 페이지로 모았다. 처음에는 지도로, 복습할 때는 체크리스트로 쓴다.
각 항목의 제목이 해당 노트 링크다. **자세한 근거와 측정 코드는 노트에 있다.**

!!! info "실측 기준"

    이 섹션의 수치는 **JDK 17.0.12 (HotSpot) · Windows 11 · 6코어**에서 직접 측정했다.
    **JUnit 5.12.2 · Spring 6.2.14 · Spring Boot 3.5.8 · Mockito 5.17.0 · Logback 1.5.34 ·
    Micrometer 1.15.12 · HikariCP 6.3.3**을 썼다. 마이크로벤치마크는 워밍업 뒤 7~9회의 **중앙값**이고,
    컨텍스트 측정은 **그룹마다 JVM을 새로 띄워** 앞 그룹의 클래스 로딩 효과를 배제했다 —
    처음에 한 JVM에서 이어 쟀다가 **결론이 뒤집히는 값**이 나왔고, 그것 자체가 이 섹션의 교훈 하나다.

    **도커가 없는 환경이라 Testcontainers는 실측하지 못했고, 그래서 관련 수치는 적지 않았다.**

## 이 섹션을 관통하는 흐름

```text

   단위 · 통합 테스트          Mock · 슬라이스 · 컨테이너      로그 · 메트릭 · 트레이싱     장애 분석과 성능 개선
   컨텍스트가 전부다            컨텍스트가 또 전부다            메트릭 10 ns, 로그 5,008 ns   대기 시간이 전부다

   싸게 많이 검증한다     →    필요한 만큼만 진짜로     →     미리 신호를 심어 둔다    →    계산으로 병목을 확정한다
```

## ① 무엇을 어떻게 검증할까

### [단위 테스트와 통합 테스트](단위-통합-테스트/단위-통합-테스트.md)

둘을 가르는 기준은 "무엇을 검증하는가"가 아니라 **"무엇을 준비해야 하는가"** 다.

* **순수 단위 테스트는 한 개당 0.36 ms**였다(2,000개 1,180 ms의 기울기). JUnit 고정 비용이 약 350 ms, JVM 기동이 약 235 ms 따로 있다.
* **컨텍스트 로드는 빈 개수에 거의 비례**했다 — 빈 9개 **7.0 ms** / `@SpringBootTest`(173개) **170 ms** / 내장 톰캣(282개) **265 ms**.
* 단위 테스트 1개 추가 **0.36 ms** vs 컨텍스트 1개 추가 **265 ms** → **736배**. 이 숫자가 테스트 피라미드의 근거다.
* **"통합 테스트가 느리다"는 절반만 맞다.** 컨텍스트는 캐시된다. `@SpringBootTest` 20개가 **컨텍스트를 공유하면 3,570 ms**, `@DirtiesContext`로 매번 버리면 **9,180 ms(2.6배)** 였다. 재로드 1회가 **295 ms**다.
* **캐시 키는 설정 클래스·프로파일·프로퍼티·웹 환경·빈 오버라이드**로 만들어지고 **하나라도 다르면 새 컨텍스트**다. 상한은 기본 **32개**이며, 넘으면 **오류 없이 느려지기만** 한다.
* **최초 로드와 이후 로드가 73~86배 차이** 났다(빈 9개 기준 670 ms vs 7.0 ms). 대부분은 컨텍스트가 아니라 **클래스 로딩** 비용이다.
* **테스트를 빠르게 만드는 건 결국 설계다.** 필드 주입이면 컨텍스트 없이 객체를 만들 수조차 없어 모든 테스트가 통합 테스트가 된다.

## ② 가짜와 진짜를 어떻게 섞을까

### [Mock · Spring Test · Testcontainers](Mock-SpringTest-Testcontainers/Mock-SpringTest-Testcontainers.md)

목을 쓰는 이유는 빠르기 때문이 **아니다.** 오히려 느리다.

* 호출 1회 실측 — **실제 구현 3.6 ns · 손으로 만든 페이크 7.0 ns · Mockito 목 4,331 ns**. **621배**다.
* 그런데도 쓰는 이유는 **결제 타임아웃처럼 진짜로는 만들 수 없는 경로를 한 줄로 재현**할 수 있어서다.
* **목은 호출을 전부 기록한다.** 실측 **호출 1회당 301 B**, 100만 회에 힙 **287 MB**. 반복문에서 쓰다가 실제로 `OutOfMemoryError`를 냈다.
* `mock()` **첫 호출은 1,011 ms**(바이트코드 생성), 이후 **100.6 µs**. `when()` 105.9 µs, `verify()` 36.4 µs.
* 목이 왜 4 µs인지 **세 가지 가설을 확인했는데 전부 아니었다** — 누적 호출 수 무관, 스택 깊이 무관, 인라인 목 메이커도 12% 차이뿐. **프록시 고정 비용**으로 보는 것이 정확하다.
* **스프링 테스트의 진짜 비용은 컨텍스트다.** `@WebMvcTest` 빈 **108개 · 207 ms** vs `@SpringBootTest` 빈 **292개 · 348 ms**.
* **`@MockitoBean` 한 줄이 컨텍스트를 하나 더 만든다.** 빈 오버라이드가 캐시 키의 일부이기 때문이다. 테스트 4개에 컨텍스트 3개가 되어 3,598 → **4,956 ms**가 됐다. **목 4 µs가 만든 컨텍스트는 348 ms — 8만 배**다.
* **"목이 기본"이 아니다.** 저장소처럼 동작을 흉내 낼 수 있으면 페이크가 낫다. **`verify()`는 결과로 확인할 방법이 없을 때**(알림·이벤트)만 쓴다.
* Testcontainers는 **H2에서만 통과하는 코드**(예약어 `rank`, 함수 지원, 정렬 규칙)를 막는다. 컨테이너는 **`static`으로 재사용**한다.

## ③ 배포 후엔 무엇을 볼까

### [로그 · 메트릭 · 트레이싱](로그-메트릭-트레이싱/로그-메트릭-트레이싱.md)

셋은 **같은 것의 세 가지 해상도**다. 메트릭이 "무엇이", 트레이스가 "어디가", 로그가 "왜"를 답한다.

* **메트릭은 사실상 공짜다** — `Counter.increment()` **10.0 ns**, `Timer.record()` **20.7 ns**. **로그 한 줄은 5,008 ns로 500배**다.
* **가장 아까운 낭비는 끈 로그다.** `DEBUG`를 꺼도 `log.debug("주문 " + order)`는 **128.5 ns**를 먹는다(문자열을 먼저 만들고 버린다). `{}` 플레이스홀더면 **3.4 ns, 38배** — 측정 하한(4.1 ns)과 같다.
* **`AsyncAppender`는 싱크를 빠르게 만들지 않는다.** 비동기만 켜면 5,008 → **3,724 ns(1.3배)** 뿐이었다. `immediateFlush=false`가 **1,326 ns(3.8배)** 로 훨씬 컸고, **둘 다 하면 754 ns(6.6배)** 였다.
* **`neverBlock=true`는 로그를 버리는 옵션이다.** 싱크가 느린 채로 켜니 **77.5%가 사라졌다.** `discardingThreshold` 기본값도 **20**이라 큐 여유 20% 미만이면 `INFO` 이하를 조용히 버린다.
* 로그 1줄 **94.6 B** → 초당 1만 줄이면 하루 **81.7 GB**.
* **MDC는 `ThreadLocal`이라 스레드를 넘지 못한다.** 실측에서 풀 스레드의 `traceId`가 **`null`** 이었고, `getCopyOfContextMap()`으로 넘겨야 유지됐다. **`finally`에서 `clear()`를 빠뜨리면 다음 요청에 남아 없는 것보다 나쁘다.**
* 메트릭의 위험은 속도가 아니라 **태그 카디널리티**다. 태그 값 10만 종 → 미터 10만 개, 힙 **37.5 MB**(미터당 383 B). `userId`·`orderId`는 태그가 아니라 **로그에 넣는다.**
* 매번 `registry`에서 이름으로 찾으면 **91.5 ns(9배)** 다. 생성자에서 미리 받아 둔다.
* **백분위는 히스토그램 쪽이 쌌다**(36.6 vs 135.3 ns) — 기대 범위를 지정해 버킷이 줄어서다. 게다가 **인스턴스별 백분위는 합칠 수 없어** 여러 대면 히스토그램이 맞다.

## ④ 문제가 나면 어떻게 좁힐까

### [장애 분석과 성능 개선](장애분석-성능개선/장애분석-성능개선.md)

**"CPU도 낮은데 느리다"는 거의 언제나 대기 문제다.**

* 처리 시간이 **5 ms로 내내 고정**인데 이용률만 올리자 p99가 이렇게 변했다 — **30% 10.0 → 70% 14.2 → 90% 26.0 → 95% 37.6 → 99% 57.1 → 110% 562.5 ms**.
* **곡선이 비선형이다.** 30→90%(3배)에 p99 2.6배인데, 90→99%(1.1배)에 다시 **2.2배**다. **100%를 넘으면 평형이 없어** 대기열이 무한히 자란다(110%에서 길이 171.8).
* **그래서 여유 30%는 낭비가 아니라 완충 장치다.**
* **처리량 상한은 계산된다** — `동시 처리 개수 ÷ 보유 시간`. 풀 10 ÷ 0.0308초 = **325건/초**였고 실측이 **316~334건/초**로 맞았다.
* **스레드를 늘리는 건 대책이 아니다.** 동시 스레드를 **5 → 160개(32배)** 늘려 처리량은 **153 → 334건/초(2.2배)**, 타임아웃은 **0 → 1,119건**이 됐다.
* **병목을 늘려야 는다.** 풀을 **5 → 80개** 늘리자 **169 → 1,908건/초(11.3배)**. 다만 풀 40·80은 이론값에 못 미쳤는데 **병목이 CPU로 옮겨 갔기 때문**이다.
* **풀 크기 × 서버 대수**를 DB의 최대 연결 수와 항상 대조한다. 서버 10대 × 풀 80이면 DB 연결 800개다.
* **스레드 덤프는 세 가지 모양**으로 읽는다 — 데드락은 JVM이 직접 찾아 주고(`findDeadlockedThreads`), 락 경합은 **같은 스택에 `BLOCKED`가 몰리고**(12개 중 11개), 느린 외부 호출은 **`TIMED_WAITING`이 쌓이는데 CPU는 0%** 다.
* **덤프는 3번 뜬다.** 한 번이면 "바쁜 것"과 "멈춘 것"을 구분할 수 없다.
* **타임아웃을 늘리는 것은 대책이 아니다.** 실패가 느린 성공이 되고 스레드는 더 오래 묶인다.

!!! danger "네 노트가 만나는 지점 — 재지 않으면 반대로 판단한다"

    이 섹션에서 **직관과 반대인 결과가 네 번** 나왔다.

    * **한 JVM에서 이어 재니** "컨텍스트 5개"가 "컨텍스트 1개"보다 빨랐다 — 앞 그룹의 클래스 로딩 덕이었다.
    * **목이 느렸다.** 페이크의 **621배**. "목은 가벼우니 마음껏"이 틀렸다.
    * **비동기 로그가 별로 안 빨랐다.** 1.3배뿐이고, `immediateFlush=false`가 3.8배로 더 컸다.
    * **스레드를 32배 늘려도 처리량은 2.2배**였다. 늘어난 건 타임아웃 1,119건이었다.

    네 번 다 **"당연히 이럴 것"이라는 예상이 실측에서 뒤집혔다.**
    그리고 목이 왜 4 µs인지는 **세 가지 가설을 다 확인했는데 전부 아니었다** —
    **모르는 것을 안다고 쓰는 것보다 모른다고 적는 편이 낫다.**

## 자주 틀리는 것

| 잘못된 이해 | 올바른 이해 |
| --- | --- |
| 통합 테스트는 느리니 적게 써야 한다 | 느린 건 개수가 아니라 **컨텍스트 종류**다. 20개가 하나를 나눠 쓰면 2.65 ms/개. |
| `@SpringBootTest`는 테스트마다 컨텍스트가 뜬다 | **캐시된다.** 설정이 같으면 클래스가 몇 개든 하나다. |
| 컨텍스트 캐시는 무제한이다 | 기본 **32개**. 넘으면 **오류 없이 느려지기만** 한다. |
| 단위 테스트가 통과하면 기능이 동작한다 | **가짜끼리는 늘 맞는다.** 매핑·제약·트랜잭션은 검증되지 않는다. |
| 목은 가벼우니 마음껏 써도 된다 | 페이크의 **621배**이고 **호출당 301 B**를 쌓는다. |
| `@MockitoBean`은 목 하나 만드는 비용이다 | **컨텍스트가 하나 더** 생긴다. 4 µs vs 348 ms. |
| H2로 테스트하면 MySQL도 문제없다 | 예약어·함수·정렬이 달라 **H2에서만 통과하는 코드**가 생긴다. |
| `DEBUG`를 꺼 두면 로그 비용은 0이다 | 문자열 연결이면 **128.5 ns**다. |
| 비동기 어펜더를 켜면 로그가 공짜가 된다 | 싱크가 느리면 **1.3배**뿐. 버퍼링이 3.8배로 더 크다. |
| `neverBlock=true`는 성능 옵션이다 | **로그를 버리는 옵션**이다. 실측 **77.5%** 유실. |
| 태그는 자세할수록 좋다 | 10만 종이면 미터 10만 개, 힙 **37.5 MB**다. |
| `traceId`는 프레임워크가 알아서 넘겨 준다 | MDC는 `ThreadLocal`이다. 풀에 넘기면 **`null`**. |
| CPU가 낮으면 서버는 한가하다 | **기다리는 중**일 수 있다. 풀 스레드 전부 `TIMED_WAITING`인데 CPU 0%. |
| 느리면 스레드를 늘리면 된다 | **32배** 늘려 처리량 **2.2배**, 타임아웃 **1,119건**. |
| 이용률 90%면 아직 여유가 있다 | p99가 이미 처리 시간의 **5.2배**다. 95%부터 손쓸 수 없다. |
| 타임아웃을 늘리면 실패가 준다 | **느린 성공**으로 바뀌고 스레드는 더 오래 묶인다. |
| 풀은 크게 잡을수록 좋다 | 서버 10대 × 풀 80이면 DB 연결 **800개**다. |
| 스레드 덤프 한 번이면 충분하다 | **순간의 사진**이다. 3번 떠서 비교한다. |
| 평균 응답 시간이 괜찮으면 괜찮다 | 이용률 90%에서 p50 8.4 ms인데 **p99 26.0 ms**였다. |
| 병목을 고치면 성능 문제가 끝난다 | **다음 병목이 드러난다**(풀 → CPU). 재측정이 필수다. |

## 면접 직전에 이것만

!!! note "네 문장으로"

    1. **테스트에서 비싼 것은 개수가 아니라 컨텍스트 종류**다. 단위 테스트 **0.36 ms** vs 컨텍스트 **265 ms**(736배)이고,
       `@SpringBootTest` 20개도 캐시를 공유하면 3,570 ms, `@DirtiesContext`면 9,180 ms다.
    2. **목의 값어치는 속도가 아니라 재현성**이다. 페이크의 **621배**로 오히려 느리고,
       **`@MockitoBean` 한 줄이 컨텍스트를 하나 더**(348 ms) 만든다. 슬라이스는 빈을 292 → 108개로 줄인다.
    3. **로그·메트릭·트레이스는 해상도가 다른 단계**다. 메트릭 **10 ns**, 로그 **5,008 ns**.
       **비동기는 싱크를 빠르게 만들지 않고**(1.3배), `neverBlock`은 **77.5%를 버린다.**
    4. **"CPU 낮은데 느리다"는 대기 문제**다. 이용률 곡선은 비선형이라 90%부터 무너지고,
       처리량 상한은 **`동시 처리 개수 ÷ 보유 시간`** 으로 계산된다(325건/초, 일치).
       **스레드를 32배 늘려도 2.2배**다.
