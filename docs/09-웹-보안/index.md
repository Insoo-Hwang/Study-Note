# 09. 웹 · 보안 — 한 페이지 요약

> **요청은 통로를 열고, 규약에 따라 실리고, 신원을 달고, 검사를 통과해야 비로소 처리된다. 네 노트는 그 네 단계이고, 관통하는 질문은 하나다 — 클라이언트가 보낸 값을 어디까지 믿을 것인가.**

이 섹션 노트 4개의 핵심만 한 페이지로 모았다. 처음에는 지도로, 복습할 때는 체크리스트로 쓴다.
각 항목의 제목이 해당 노트 링크다. **자세한 근거와 측정 코드는 노트에 있다.**

!!! info "실측 기준"

    이 섹션의 수치는 **JDK 17.0.12 (HotSpot) · Windows 11**에서 직접 측정했다. TLS·Keep-Alive·
    멱등성·ETag는 **127.0.0.1 루프백**에서, 단계별 분해와 HTTP/2 비교는 **외부 공개 사이트**에서 쟀다.
    **루프백은 RTT와 대역폭이 사실상 공짜라 왕복·바이트를 아끼는 최적화가 시간으로 드러나지 않는다** —
    이 성질 때문에 실제로 두 번이나 예상과 다른 결과가 나왔고, 그 자체가 이 섹션의 교훈 하나다.

## ① 통로를 연다

### [HTTP · TCP 네트워크](HTTP-TCP-네트워크/HTTP-TCP-네트워크.md)

요청 하나가 느린 이유는 대개 "서버가 느려서"가 아니라 **"말을 걸기까지가 오래 걸려서"** 다.

* 요청은 서버에 닿기 전에 **세 번 준비**한다 — **DNS 10.5 ms · TCP 10.9 ms · TLS 16.3 ms**. 서버 코드가 한 줄도 돌기 전의 비용이다.
* 준비 비용은 **RTT에 비례**해서 **서버를 아무리 빠르게 만들어도 줄지 않는다.** 그래서 대책은 "빠르게"가 아니라 **"다시 하지 않기"** 다.
* 실측에서 요청 1회가 **매번 새 TLS 연결 22.52 ms → Keep-Alive 1.56 ms**로 **14.4배** 빨라졌다.
* 같은 실험을 평문 HTTP로 하면 **1.9배**뿐이었다. **이 차이가 새 연결 비용의 대부분이 TLS라는 것**을 말해 준다.
* **재사용의 이득은 응답이 빠를수록 크다.** 서버가 3 ms인 API면 13.6배, 229 ms인 API면 1.2배다.
* 요청 헤더는 최소 42 B인데 실제 브라우저는 **686 B(16.3배)** 였고, **매 요청 반복**된다.
* 동시 20요청에서 **HTTP/1.1 전체 404 ms · p50 242 ms**, **HTTP/2 전체 147 ms · p50 56 ms**였다. **p50 차이(4.3배)가 전체 차이(2.7배)보다 큰 것**이 핵심 — 뒤에 선 요청이 앞을 안 기다린다.
* **타임아웃은 연결·읽기·풀 대기 세 개를 모두** 건다. 특히 읽기 타임아웃이 없으면 **오류도 없이 스레드만 조용히 묶인다.**

## ② 무엇을 실을지 정한다

### [REST와 API 설계](REST-API-설계/REST-API-설계.md)

REST의 값어치는 URL이 예뻐지는 것이 아니라, **중간 장치가 본문을 열지 않고도 캐시·재시도를 판단**할 수 있다는 데 있다.

* **멱등성이 실무 문제인 이유**는 타임아웃 때문이다. 응답을 못 받으면 클라이언트는 **서버가 못 받은 건지 처리하고 응답만 못 준 건지 구분할 수 없다.**
* 같은 요청을 5번 보낸 실측이다. **`POST` 주문 5개 · `PUT` 1개 · `PATCH(+1)` 수량 5 · `PUT(=10)` 수량 10.**
* **메서드 이름이 아니라 연산의 성격이 멱등성을 정한다.** `PATCH`도 절대값을 지정하면 멱등하고, `PUT`으로 상대값 연산을 하면 깨진다.
* `POST`는 멱등하게 만들 수 없다. **`Idempotency-Key`로 서버가 중복을 판별**하고, **중복 요청에 오류가 아니라 저장된 같은 응답**을 돌려줘야 한다.
* **4xx와 5xx를 나누는 실질적 이유는 재시도**다. 서버 오류를 400으로 내리면 재시도되어야 할 요청이 재시도되지 않는다.
* `ETag` 조건부 요청으로 본문이 **21,996 B → 0 B(100% 절약)** 가 됐다. **그런데 시간은 안 줄었다**(640 vs 677 ms) — 아끼는 것이 **시간이 아니라 바이트**이기 때문이다.
* 반면 gzip은 같은 JSON을 **2,277 B(9.7배, 90% 절약)** 로 줄여 **어디서나 이득**이다.
* `ShallowEtagHeaderFilter`는 **응답을 다 만든 뒤** 해시를 내므로 **서버 부하를 못 줄인다.** 줄이려면 `checkNotModified`로 **본문 생성 전에** 304를 반환한다.

## ③ 신원을 싣는다

### [쿠키 · 세션 · JWT](쿠키-세션-JWT/쿠키-세션-JWT.md)

**쿠키는 인증 방식이 아니라 운반 수단**이다. 세션 ID도 JWT도 쿠키에 담긴다.

* 세션은 **서버가 정보를 갖고 열쇠만** 주고, JWT는 **정보를 서명해 클라이언트가 들고 다닌다.** 여기서 모든 차이가 나온다.
* 쿠키 크기 실측은 **세션 43 B vs JWT 221 B(5.1배)** 다. 요청 **100만 건이면 169.8 MB**를 더 보낸다.
* **JWT payload는 암호화가 아니라 Base64url 인코딩이다.** 키 없이 디코딩하니 `{"sub":"1234567890","role":"ROLE_USER",...}`가 **그대로 읽혔다.** 서명은 **위조를 막을 뿐 내용을 감추지 않는다.**
* **JWT의 진짜 약점은 크기가 아니라 무효화다.** 서버가 상태를 안 갖는다는 것은 **로그아웃시킬 방법이 없다**는 뜻이다.
* 블랙리스트를 두면 무효화는 되지만 **매 요청 저장소를 조회하게 되어 JWT를 쓴 이유가 사라진다.** 그래서 **짧은 Access + 서버 저장 Refresh**로 절충한다.
* 알고리즘은 **HS256 서명 2.48 µs(초당 402,606회)** vs **RS256 서명 2,258.3 µs(초당 442회)** 로 **909배** 차이였다.
* 다만 **RS256은 검증이 96.2 µs로 서명의 1/23**이다. **서명은 인증 서버에서 드물게, 검증은 모든 서비스에서 자주** 일어나므로 비싼 쪽이 드문 쪽이라 감당이 된다.
* **HS256의 진짜 문제는 성능이 아니라 신뢰 범위다.** 검증하려면 서명 키가 필요한데, 그 키를 받은 서비스는 **토큰을 위조할 수도** 있다.
* 로그인 성공 시 **세션 ID를 반드시 재발급**한다. 안 그러면 공격자가 미리 심어 둔 ID가 로그인된 세션이 되는 **세션 고정 공격**에 당한다.

## ④ 그 신원을 검사한다

### [인증 · 인가 · CORS · CSRF](인증인가-CORS-CSRF/인증인가-CORS-CSRF.md)

**인증은 "누구인가", 인가는 "무엇을 해도 되는가"** 이고 각각 **401·403**으로 답한다.

* 비밀번호를 SHA-256으로 저장하는 것은 거의 안 한 것과 같다. 실측 **0.388 µs, 단일 스레드 초당 2,580,440회** — **8자리 소문자+숫자 전체가 303.7시간**이면 뚫린다(GPU면 훨씬 빠르다).
* **그래서 비밀번호 해시는 일부러 느리게 만든다.** PBKDF2 반복이 **1,000회 1.6 ms · 10만 회 140.2 ms · 60만 회 864.4 ms**였고, 60만 회는 SHA-256의 **223만 배**다.
* **공격자와 서버가 같은 비용을 치르는 것이 이 방어의 원리다.** 초당 258만 번 시험하던 공격자가 **초당 1번**이 된다.
* **반복 횟수와 솔트는 막는 것이 다르다.** 반복은 **한 번의 시도를 비싸게**, 솔트는 **미리 만든 표의 재사용을** 막는다. 솔트는 비밀이 아니어도 된다.
* 대가도 있다. 60만 회면 **코어 하나로 초당 1회**라 로그인 엔드포인트가 **DoS 표면**이 된다. 레이트 리밋이 함께 필요하다.
* **가장 흔하고 조용한 취약점은 인가 누락**이다. `/orders/{id}`에서 소유자를 확인하지 않으면 번호만 바꿔 남의 주문이 보이는데, **컴파일도 되고 테스트도 통과하고 오류도 안 난다.**
* **CORS 오류는 서버가 요청을 거부한 것이 아니다.** 서버는 정상 처리했고 부수 효과까지 일어났으며, **브라우저가 응답을 스크립트에 안 넘긴 것**뿐이다. `curl`로는 되고 브라우저에서만 실패하는 이유다.
* **CORS는 제한을 푸는 규약이지 거는 규약이 아니다.** 넓게 열수록 약해진다.
* **CSRF는 방향이 반대다.** CORS가 "응답을 못 읽게"라면 CSRF는 **"요청은 이미 나갔다"** 는 문제다. 응답을 못 읽어도 **이체는 끝났다.**
* 방어의 공통 원리는 **"쿠키가 아닌 곳에서 증표를 받는다"** 이다. CSRF 토큰이든 `SameSite`든 `Authorization` 헤더든 같다.

!!! danger "네 노트가 만나는 지점 — 루프백은 거짓말을 한다"

    이 섹션에서 **두 번이나 예상과 다른 결과**가 나왔고, 원인이 같았다.

    * **TLS 세션 재개**가 루프백에서 이득이 없었다(16.31 vs 17.24 ms). 재개가 아끼는 것은 **왕복**인데 루프백은 왕복이 공짜다.
    * **`ETag` 304 응답**이 더 빠르지 않았다(640 vs 677 ms). 조건부 요청이 아끼는 것은 **바이트**인데 루프백은 대역폭이 무한하다.

    **왕복과 바이트를 아끼는 최적화는 왕복과 바이트가 비쌀 때만 시간으로 나타난다.**
    측정 환경이 결론을 뒤집을 수 있다는 뜻이고, 그래서 **어디서 쟀는지를 늘 함께 적어야 한다.**

## 자주 틀리는 것

| 잘못된 이해 | 올바른 이해 |
| --- | --- |
| API가 느리면 서버가 느린 것이다 | 준비 비용만 **37.7 ms**였다. 서버가 3 ms여도 체감은 40 ms다. |
| HTTPS는 느리니 내부 통신은 HTTP로 | 느린 것은 **핸드셰이크**지 전송이 아니다. 재사용하면 차이가 거의 없다. |
| 연결 재사용은 미미한 최적화다 | 실측 **14.4배**다. 응답이 빠른 API일수록 비중이 커진다. |
| HTTP/2를 쓰면 head-of-line blocking이 없다 | 애플리케이션 계층만 해결했다. **TCP 계층에는 남아** 패킷 유실 시 전체가 멈춘다. |
| 타임아웃이 나면 요청이 처리 안 된 것이다 | 알 수 없다. **처리하고 응답만 못 줬을 수도** 있다. |
| `PUT`을 쓰면 자동으로 멱등해진다 | **서버 구현이 정한다.** 상대값 연산이면 `PUT`이어도 깨진다. |
| 중복 요청에는 409를 주면 된다 | 오류를 주면 **또 재시도**한다. **저장된 같은 응답**을 줘야 한다. |
| `ETag`를 켜면 서버가 빨라진다 | **대역폭만 아낀다.** 실측에서 304가 오히려 677 ms(전체 640 ms)였다. |
| 쿠키와 세션은 다른 인증 방식이다 | 쿠키는 **운반 수단**이다. 세션 ID도 JWT도 쿠키에 담긴다. |
| JWT는 암호화되어 있어 안전하다 | **인코딩일 뿐이다.** 키 없이 payload가 그대로 읽혔다. |
| JWT는 상태가 없어 로그아웃도 잘 된다 | **로그아웃이 가장 어려운 부분**이다. 만료 전까지 유효하다. |
| 블랙리스트를 두면 JWT 문제가 해결된다 | 매 요청 조회하게 되어 **JWT를 쓴 이유가 사라진다.** |
| RS256은 느려서 못 쓴다 | 느린 것은 **서명(초당 442회)** 이고 검증은 초당 10,400회다. 서명은 드물다. |
| 비밀번호를 해시했으니 안전하다 | SHA-256은 **초당 258만 회**다. 8자리가 303시간이면 뚫린다. |
| 해시는 빠를수록 좋다 | 비밀번호에서는 **느릴수록** 좋다. 공격자도 같은 속도를 쓴다. |
| 솔트를 쓰면 무차별 대입이 막힌다 | 솔트가 막는 것은 **표 재사용**이다. 대입은 **반복 횟수**가 막는다. |
| 로그인만 확인하면 인가는 된 것이다 | `/orders/{id}`의 **소유자 확인 누락**이 가장 흔한 취약점이다. |
| CORS 오류는 서버가 요청을 거부한 것이다 | **서버는 정상 처리했다.** 브라우저가 응답을 안 넘긴 것뿐이다. |
| CORS를 설정하면 보안이 강해진다 | CORS는 제한을 **푸는 쪽**이다. 넓게 열수록 약해진다. |
| CORS를 막으면 CSRF도 막힌다 | 다르다. CSRF는 **요청이 이미 나가서** 처리된다. |
| REST API는 CSRF 방어가 필요 없다 | **쿠키로 인증하면 필요하다.** 불필요한 건 Bearer 헤더를 쓸 때다. |

## 면접 직전에 이것만

!!! note "네 문장으로"

    1. **응답 시간은 준비 + 왕복 + 서버 + 전송의 합**이고, 준비는 RTT에 비례해 서버 개선으로 안 줄어든다.
       그래서 **연결을 재사용**한다 — 실측 **22.52 → 1.56 ms(14.4배)**.
    2. **멱등성은 재시도를 안전하게 만드는 계약**이다. 같은 요청 5번에 `POST`는 5개, `PUT`은 1개를 만들었고,
       `POST` 재시도에는 **`Idempotency-Key`와 "같은 응답 반환"** 이 필요하다.
    3. **세션과 JWT는 상태를 누가 갖느냐로 확장성과 무효화가 정반대**다. JWT payload는 **암호화가 아니고**,
       **로그아웃이 안 되는 것**이 가장 큰 약점이라 짧은 Access + 서버 저장 Refresh로 절충한다.
    4. **비밀번호 해시는 일부러 느리게** 만든다. SHA-256이면 8자리가 **303시간**, PBKDF2 60만 회면
       **223만 배** 느려진다. 그리고 **인가 누락과 CORS/CSRF 혼동**이 실무에서 가장 흔한 사고다.
