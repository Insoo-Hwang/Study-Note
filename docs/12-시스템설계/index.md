# 12. 시스템 설계 — 한 페이지 요약

> **시스템 설계는 기술을 고르는 시험이 아니라 "틀리면 안 되는가 · 몇 건인가 · 지금 보여야 하는가"에 답하고 그 답에서 설계를 끌어내는 시험이다. 같은 +1이라도 쿠폰은 100장이 1,000장으로 새지 않게 원자적으로 막고, 조회수는 64,000번의 UPDATE를 1번으로 모은다.**

이 섹션 노트 5개의 핵심만 한 페이지로 모았다. 처음에는 지도로, 복습할 때는 체크리스트로 쓴다.
각 항목의 제목이 해당 노트 링크다. **자세한 근거와 측정 코드는 노트에 있다.**

!!! info "측정 기준"

    수치는 **JDK 21.0.12.1 (Temurin) · Windows 11 · 6코어**에서 직접 실행한 값이다. DB 동시성은
    **H2 1.4.200 인메모리(READ COMMITTED)**, 커넥션 풀은 **HikariCP 4.0.3**, 대량 처리와 랭킹 쿼리는
    **SQLite 3.50.4 파일 DB(100만 행)** 로 쟀다. 결제 타임아웃 · 윈도우 · 늦은 이벤트는 **시드를 고정한
    최소 모델**이다. **Redis는 이 환경에서 띄우지 않았다** — Redis 수치는 공식 문서(AOF · HyperLogLog ·
    `ZADD`)와 08 섹션의 실측(Redis 7.4)을 인용했다.

## 이 섹션을 관통하는 흐름

```text
① 어떻게 답하는가            ② 한 건이 정확해야 할 때             ③ 규모와 시간이 문제일 때
   시스템 설계 답변법            선착순 쿠폰 · 주문 결제               대용량 처리 · 실시간 처리
   요구사항 → 숫자 → 병목        check-then-act · "모름" 상태          청크 · 커서 · 체크포인트
   11.6 QPS · p99 · 가용성 곱    100장 → 1,000장 · 이중 결제 275건     Sorted Set · 윈도우 · HLL

   숫자가 설계를 정한다   →   확인과 변경을 한 번에 묶는다   →   늦어도 다 / 다 못 봐도 지금
```

## ① 어떻게 답하는가

### [시스템 설계 답변법](시스템설계-답변법/시스템설계-답변법.md)

**요구사항과 숫자를 먼저 잡으면 기술 선택이 따라 나온다.** 기술 이름은 병목을 확인한 뒤에야 등장한다.

* 답변은 8단계다 — **요구사항 → 규모 추정 → 가장 단순한 설계 → 저장·조회 구조 → 병목 → 확장 → 장애·정합성 → 단점.**
* **하루는 86,400초.** 하루 100만 건 쓰기는 평균 **11.6 QPS**라 DB 한 대로 충분하고, 그 100배인 읽기 **1,157 QPS**(피크 3,472)가 캐시를 부른다.
* 무작위 7자리 Base62 키는 하루치 충돌이 0.1쌍이지만 **5년치(18.25억 개)는 472,883쌍** — 하루만 보면 틀린 결론을 낸다.
* **처리량은 가장 느린 공유 자원이 정한다.** DB 동시 8개에서 앱 스레드를 16 → 128로 늘려도 **506 → 500 req/s**, 지연만 **31.9 → 231.7 ms**. 상한은 8 ÷ 15.46 ms = 517로 먼저 계산된다.
* **평균은 분포를 숨긴다.** 평균 30.7 ms인 분포의 p99.9가 **1,178.8 ms**. 1%가 느린 백엔드를 **10개** 병렬 호출하면 **9.63%**, **100개**면 **63.38%**가 느리다.
* **가용성은 직렬로 곱해진다.** 99.9% 3개 직렬 = **99.70%**(연 26.25시간), 독립 이중화 2대 = **99.9999%**.
* 모든 선택에 **"무엇을 얻고 무엇을 잃었는가"** 를 먼저 말한다.

## ② 한 건이 정확해야 할 때

### [선착순 쿠폰 시스템](선착순-쿠폰-시스템/선착순-쿠폰-시스템.md)

**확인과 차감 사이의 틈을 없애는 것이 전부다.** 조회수는 반대로 정확성 대신 처리량을 고른다.

* 락 없이 "읽고 → 100 미만 확인 → 읽은 값 + 1"을 하자 **1,000명 전원이 발급**됐다. 갱신 손실로 카운터가 17~60에 머물러 모두가 통과했다. `@Transactional`은 이것을 막지 않는다.
* **조건부 UPDATE**(`WHERE issued < total`)와 `SELECT ... FOR UPDATE`는 모두 **정확히 100장**. 확인 사이에 1 ms 작업이 끼면 **250~259 ms vs 66~72 ms** — 잠금을 쥔 시간이 차이를 만든다.
* **1인 1매는 조회가 아니라 제약으로.** 200명 × 5번 동시 클릭에 "조회 후 삽입"은 중복 **207~684건**, `UNIQUE(coupon_id, user_id)`는 **0건**.
* DB 한계를 넘으면 **Redis Lua**로 수량과 1인 1매를 한 번에 판정한다. 대신 AOF 기본 `everysec`에서 **최대 1초치 유실**(Redis 문서)이 있어 **DB 유니크 제약이 최종 방어선**이고 둘을 대사한다.
* 1만 장에 100만 명이면 **99%는 실패할 요청**이다. 매진 플래그로 DB에 닿기 전에 돌려보낸다.
* **조회수는 모았다가 한 번에.** 64,000번의 UPDATE가 **1번**이 된다. 대가는 **최대 유실 = 초당 건수 × 반영 주기**(5,000/s × 1초 = 5,000건).

### [주문 · 결제 시스템](주문-결제-시스템/주문-결제-시스템.md)

**PG는 내 트랜잭션에 들어오지 않는다.** 그래서 원자성 대신 "어긋난 것을 찾아 고치는" 장치를 겹겹이 둔다.

* 요청 유실 1% · 승인 후 응답 유실 3% 모델 1만 건 — **타임아웃을 실패로 처리하면 274건이 "돈은 나갔는데 실패"**, **멱등 키 없이 재시도하면 275건 이중 결제**.
* 같은 멱등 키로 재시도해도 **끝까지 모르는 1건**이 남는다. **`UNKNOWN` 상태 + 조회 API로 확정**하자 1만 건 모두 정확했다.
* **PG 호출을 트랜잭션 안에 두면** 풀 10개가 PG를 기다리느라 말라, PG가 2초로 느려지자 **결제와 무관한 조회 API가 100% 실패**했다. 밖으로 빼자 조회 **20,093건 모두 성공**.
* 승인 웹훅과 만료 취소 배치가 동시에 오면, 조건 없는 UPDATE는 **416~472건을 "결제됐는데 취소"로 덮어썼다.** `WHERE status = 'PENDING'`은 **0건** — 그리고 취소가 이긴 건을 **환불(보상) 대상**으로 정확히 가려낸다.
* 복구의 마지막 층은 **조회 배치(`REQUESTED`·`UNKNOWN`)와 일 단위 대사**, 그리고 덮어쓰지 않는 **감사 이력**이다.

## ③ 규모와 시간이 문제일 때

### [대용량 처리 시스템](대용량-처리-시스템/대용량-처리-시스템.md)

**한 번에 다 하지도, 한 건씩 하지도 않는다.** 청크 하나가 트랜잭션 하나다.

* 100만 행 INSERT — **1건마다 커밋 197 건/s(약 85분)**, **1만 건마다 313,790 건/s(3.2초)**. 1만 → 전체는 1.26배뿐이라 더 묶을 이유가 적다.
* 한 트랜잭션은 되돌리기 저널이 **32.6 MB**(1만 건 청크는 0.35 MB)로 불고, 잠금 · 복제 지연 · 실패 시 전부 다시가 따라온다.
* 청크를 **OFFSET으로 넘기면 전체 순회 21.60초, 커서는 0.74초(29.1배)**.
* **처리하며 조건에서 빠지는 행을 OFFSET으로 돌면 READY 10만 건 중 5만 건만 처리**하고 정상 종료한다. `JpaPagingItemReader`가 OFFSET 방식이다.
* 보조 인덱스 3개면 적재 **26.61초(13.3배)**, 적재 후 인덱스 생성은 **4.16초**.
* **체크포인트는 청크와 같은 트랜잭션에.** 따로 쓰면 재시작 시 **1,000건 중복**, 같이 쓰면 **0건**.
* 1억 행을 `Object[]`로 받으면 **22.6 GB** — 읽기도 청크로. MySQL Connector/J는 기본적으로 **ResultSet 전체를 메모리에 올린다.**
* 병렬도는 **6코어에서 6스레드 5.91배**가 최고(8스레드 4.95배), 동시 2개인 쓰기 자원이 끼면 **3.86배에서 멈춘다.**

### [실시간 처리 시스템](실시간-처리-시스템/실시간-처리-시스템.md)

**비용을 읽기에서 쓰기로 옮긴다.** 정확성이나 완전성을 조금 내주고 "지금"을 산다.

* DB 랭킹에 `score` 인덱스를 걸면 상위 10명은 **68.85 → 0.045 ms**지만 **내 등수는 꼴찌 23.61 ms**(앞사람 세기), 갱신은 **2.5배 느려진다.**
* 정렬 유지 구조는 갱신 **약 3 µs**, 상위 10명 **1 µs 미만**. Sorted Set은 span 덕분에 `ZRANK`도 O(log N)(Redis 실측 4.4 µs).
* "60초 100건" 고정 윈도우는 경계에서 **1.99초에 200건**을 통과시킨다. 슬라이딩 로그는 100건. 근사 카운터는 몰리는 트래픽에서 **평균 6.30% · 최대 56.00%** 틀린다.
* 1분 창을 즉시 닫으면 늦은 이벤트 **1.88% 누락**, 5분 기다리면 0%. **스트림은 지연을, 배치는 정확도를** 맡는다.
* HyperLogLog는 **12,288바이트 고정**으로 100만 개를 평균 **0.79%** 오차에 센다. HashSet은 **66.5 MB**. 개별 확인은 안 된다.
* 팔로워 100만 명 계정은 쓰기 팬아웃이 원격 초당 1만 건 기준 **100초** — 대형 계정만 **읽을 때 병합**하는 하이브리드.
* 2초 폴링은 **96.7%가 빈 응답**. SSE는 HTTP/2가 아니면 **브라우저 · 도메인당 6개** 연결 제한.

## 선택 기준

```text
틀리면 비용이 생기는가? (수량 · 금액 · 권한)
├─ 예 → 한 건의 정확성
│   ├─ 한 DB 안에서 끝나는가?
│   │   └─ 예 → 조건부 UPDATE · 유니크 제약 (쿠폰)
│   └─ 외부 시스템이 끼는가?
│       └─ 예 → 트랜잭션 밖 호출 · 멱등 키 · UNKNOWN + 조회 · 보상 · 대사 (결제)
└─ 아니오 → 처리량 · 지연
    ├─ 늦어도 다 처리해야 하는가? → 청크 · 커서 · 체크포인트 · 사전 집계 (대용량)
    └─ 다 못 봐도 지금 보여야 하는가? → Sorted Set · 버킷 윈도우 · HyperLogLog · SSE (실시간)

어떤 경우든 먼저
  하루 건수 ÷ 86,400 = 평균 QPS → 가장 좁은 공유 자원의 상한과 비교 → 넘을 때만 확장
```

## 자주 틀리는 것

| 잘못된 이해 | 올바른 이해 |
| --- | --- |
| 좋은 기술을 많이 넣을수록 좋은 설계다 | 요청 경로의 구성 요소마다 가용성이 곱으로 깎인다. 필요 없어서 안 넣은 것도 설계다. |
| 서버를 늘리면 처리량이 는다 | 병목이 DB면 앱 8배에 506 → 500 req/s. 지연만 7.3배. |
| `@Transactional`이면 초과 발급이 안 난다 | 옛 값을 같이 읽는 것은 막지 않는다. 100장이 1,000장. |
| 받았는지 조회하면 중복 발급을 막는다 | 조회도 check-then-act. 유니크 제약이어야 0건. |
| 타임아웃이면 결제 실패다 | "모름"이다. 실패 처리한 373건 중 274건은 돈이 나갔다. |
| PG 호출을 트랜잭션 안에 두면 롤백으로 안전하다 | 롤백은 PG를 취소 못 하고, PG가 느려지면 무관한 조회까지 100% 실패한다. |
| OFFSET은 느릴 뿐 결과는 맞다 | 처리 중 조건에서 빠지는 행이 있으면 절반을 건너뛰고 정상 종료한다. |
| 한 트랜잭션에 넣어야 안전하다 | 실패하면 전부 다시. 청크 + 같은 트랜잭션 체크포인트가 중복 0건으로 더 안전하다. |
| 랭킹은 `ORDER BY` + 인덱스면 된다 | 상위 10명만 해결. 내 등수는 앞사람을 세고 갱신은 느려진다. |
| HyperLogLog로 방문 여부도 알 수 있다 | 개수만 안다. 원소를 저장하지 않는다. |

## 면접 직전에 이것만

!!! note "네 문장으로 요약"

    **시스템 설계는 요구사항과 숫자에서 시작합니다** — 하루 100만 건은 11.6 QPS라 샤딩이 필요 없다는
    결론이 계산 한 줄에서 나오고, 처리량의 상한은 가장 느린 공유 자원이 정합니다.
    **틀리면 안 되는 한 건**은 확인과 변경을 조건부 UPDATE로 한 번에 묶고 중복은 유니크 제약으로 막으며,
    외부 결제처럼 트랜잭션 밖의 시스템이 끼면 타임아웃을 "모름"으로 두고 멱등 키 · 조회 · 보상 · 대사로
    바로잡습니다. **총량이 문제**면 청크로 커밋하고 커서로 넘기며 체크포인트를 같은 트랜잭션에 쓰고,
    **지금 보여야 하는 값**은 정렬 · 집계를 쓸 때 유지하고 근사와 늦은 이벤트 누락을 수치로 합의합니다.
