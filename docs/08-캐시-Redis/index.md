# 08. 캐시 · Redis — 한 페이지 요약

> **캐시는 같은 답을 두 곳에 두어 속도를 얻고 정합성을 내준다. 어긋남은 갱신 순서로, 비는 순간의 폭주는 한 명만 읽게 해서, 담는 비용은 자료구조로 막고, 그래도 남는 중복은 멱등성이 지킨다.**

이 섹션 노트 4개의 핵심만 한 페이지로 모았다. 처음에는 지도로, 복습할 때는 체크리스트로 쓴다.
각 항목의 제목이 해당 노트 링크다. **자세한 근거와 실측 코드는 노트에 있다.**

!!! info "실측 기준"

    이 섹션의 수치는 **Redis 7.4.10 (docker `redis:7.4-alpine`)** · **H2 2.2.224 파일 모드** ·
    **JDK 21.0.11** 에서 직접 측정한 값이다. Redis 왕복(540 µs)에는 **Windows 호스트에서 Docker
    포트 포워딩을 거치는 비용**이 포함돼 있다. 환경마다 절대값은 달라지므로 **비율과 경향**으로 읽는다.

## ① 왜 두는가

### [캐시 전략과 정합성](캐시-전략-정합성/캐시-전략-정합성.md)

캐시는 "느린 것을 빠르게" 만드는 장치가 아니라 **"같은 답을 두 곳에 두는" 장치**다. 두 곳에 두는 순간 둘이 달라질 수 있고, **캐시 설계의 거의 전부는 그 어긋남을 어디까지 허용할지 정하는 일**이다.

* **"DB가 느리니까 캐시"가 아니다.** 실측에서 **DB 단건 PK 조회 54.3 µs**가 **Redis 왕복 540 µs**보다 **10배 빨랐다.** 캐시가 값어치를 하는 곳은 단건 조회가 아니라 **무거운 계산과 원격 호출**이다(조인+집계 677.9 ms → 1,254배 이득).
* **히트율의 효과는 직선이 아니다.** 평균 응답이 80%에서 151 ms, 90%에서 76 ms, 95%에서 36 ms, **99%에서 3.6 ms**였다. 평균이 사실상 **미스율에 비례**하기 때문이다.
* 뒤집으면 **히트율은 성능 지표가 아니라 장애 지표다.** 99% → 95%로 **4%p만 떨어져도 10배** 느려진다.
* 읽기는 **Cache-Aside가 사실상 표준**이다. 캐시가 죽어도 원본을 직접 읽어 서비스가 계속 돈다.
* **쓰기에서 갈린다.** 캐시를 **갱신하지 않고 삭제**하는 이유는 **삭제가 멱등**이라 두 쓰기의 순서가 뒤집혀도 안전하기 때문이다.
* **순서가 정합성을 정한다.** 캐시를 먼저 지우고 DB를 고치면 그 사이 읽기가 **옛 값을 박제**한다. 실측 **400회 중 400회 영구 불일치**였고, 순서를 뒤집으니 **0회**였다. **코드 두 줄의 순서다.**
* 그 순서도 완벽하진 않다(읽기가 먼저 시작한 경우). **TTL이 최종 안전망**이고, 공짜가 아니다 — 키당 **82.3 B → 117.2 B(+42.4%)**.
* `@Transactional` **안에서** 캐시를 지우면 **커밋 전에 지워져** 다른 요청이 옛 값을 다시 채운다. `@TransactionalEventListener(AFTER_COMMIT)`으로 미룬다.

| 쓰기 전략 | 쓰기 직후 읽기 | 유실 위험 | 순서 뒤집힘 | 실무 빈도 |
| --- | --- | --- | --- | --- |
| Write-Through | 히트 | 없다 | **취약** | 보통 |
| Write-Around | 미스 | 없다 | 해당 없음 | 보통 |
| Write-Back | 히트 | **있다** | 취약 | 드물다 (카운터류) |
| **무효화(삭제)** | 미스 | 없다 | **안전 (멱등)** | **가장 흔하다** |

## ② 비는 순간

### [Cache Stampede와 Request Collapsing](Cache-Stampede/Cache-Stampede.md)

**캐시는 있을 때가 아니라 비는 순간에 서비스를 죽인다.** 히트율 99%로 잘 돌던 서비스가 인기 키 하나가 만료되는 그 순간 **100% 미스**가 된다.

* 원인은 한 줄이다. **첫 요청이 캐시를 채우기 전까지 뒤따르는 요청이 전부 미스**다. 그래서 **몰리는 창의 길이 = 원본 조회 시간**이다.
* 실측했다. 원본 **327.6 ms**에 동시 요청 100개면 **DB 호출 100회 · 전체 28,136 ms · p50 15,339 ms**. **같은 답을 100번 만들었고 99번은 순수한 낭비다.**
* **캐시를 붙인 이유가 원본이 느려서였으니, 캐시가 꼭 필요한 곳일수록 스탬피드도 심하다.**
* **Request Collapsing**(single-flight)은 `ConcurrentHashMap.putIfAbsent`로 진행 중인 조회의 `Future`를 공유해 **한 명만 원본을 읽게** 한다. → **DB 1회 · 238 ms(118배)**. 다만 **서버당 1회**라 10대면 10회다.
* **Redis 분산 락**은 전체 1회로 줄이지만 폴링 때문에 **오히려 느렸다**(380 ms, 재시도 1,059회). **락을 못 잡으면 예외가 아니라 원본을 직접 읽는 경로**를 둔다.
* **논리적 만료**는 값 안에 만료 시각을 두고 **옛 값을 주면서 뒤에서 갱신**한다. **p50 0 ms — 아무도 기다리지 않았다.** 대신 100개 전부가 옛 값을 받았고, **값이 아예 없는 첫 진입은 못 막는다.** 그래서 실무에서는 **논리적 만료 + Collapsing**을 겹쳐 쓴다.
* **TTL 지터는 선택이 아니다.** 10,000개 키를 같은 TTL로 넣었더니 **6초 구간에 통째로** 만료됐다. 0~5초 지터를 주자 5개 구간(128 / 3,655 / 1,052 / 3,132 / 2,033)으로 흩어졌다.

| | Cache Stampede | Cache Penetration | Cache Avalanche |
| --- | --- | --- | --- |
| 원인 | **있던 키가 만료** | **애초에 없는 키** | **대량의 키가 동시에 사라짐** |
| 원본에 가는 요청 | 같은 키 수백 개 | **다 다른 키** | 전체 키 |
| 공격 가능성 | 낮다 | **높다** | 낮다 |
| 대책 | Collapsing · 분산 락 · 논리적 만료 | **"없음" 캐시 · 블룸 필터** | **TTL 지터 · 워밍 · 서킷 브레이커** |

**이름이 비슷하지만 대책이 서로 안 통한다.** 이 구분이 면접에서 자주 나온다.

## ③ 무엇에 담는가

### [Redis 자료구조와 활용](Redis-자료구조/Redis-자료구조.md)

Redis가 빠른 이유는 "메모리에 있어서"가 아니라 **자료구조를 서버 안에 두어 왕복과 계산을 없앴기 때문**이다. 그래서 **자료구조를 고르는 일이 곧 성능을 고르는 일**이다.

* Memcached라면 "랭킹 100명"을 얻으려고 전체를 내려받아 애플리케이션에서 정렬해야 한다. Redis는 `ZREVRANGE key 0 99` 한 번, 실측 **6.0 µs**다. 10만 명 중 "내 등수"도 **4.4 µs**다.
* **명령 실행은 싱글 스레드다.** `INCR`·`SETNX`가 공짜로 원자적인 대신, **느린 명령 하나가 전체를 멈춘다.** 100만 키에서 `KEYS`를 돌리자 다른 클라이언트의 `GET` 지연이 **평균 0.35 → 14.87 ms(42배), 최대 2 → 636 ms(318배)** 로 뛰었다.
* **Redis 7의 `io-threads`는 소켓 입출력만 나눈다.** 명령 실행은 여전히 스레드 하나다.
* **복잡도가 곧 지연이다.** `GET` 5.2 µs 대 `KEYS`(100만) **158 ms** — **3만 배**다. `HGETALL`(10만 필드) 54 ms, `LRANGE 0 -1` 22.5 ms도 같은 이유로 위험하다.
* **같은 데이터라도 그릇에 따라 메모리가 3배 차이 난다.** 사용자 이름 1,000건을 String 1,000개로 담으면 80,256 B, 100개씩 Hash 10개로 나누면 **26,352 B(3.05배 절약)** 였다.
* 그 절약의 정체는 **내부 인코딩**(`listpack`·`intset`)이다. **임계값을 한 개 넘기는 순간 계단처럼 뛴다** — 정수 Set 512→513개 **18.6배**, ZSet 128→129개 **13배**. 임계값 기본값은 배포판마다 달라 **`CONFIG GET`으로 확인**한다.
* **파이프라이닝은 코드 한 줄로 얻는 가장 큰 개선이다.** 같은 `SET` 10만 건이 15,015 rps → 16개 묶음 229,358 rps → 100개 묶음 **714,286 rps(47.6배)** 였다.

| 요구사항 | 자료구조 | 고르는 이유 |
| --- | --- | --- |
| 랭킹 · 내 등수 | **Sorted Set** | `ZRANK` O(log N), 실측 4.4 µs |
| 객체의 일부 필드만 갱신 | **Hash** | `HSET`·`HINCRBY`가 원자적 (**필드별 TTL은 없다**) |
| 좋아요 누른 사람 "확인" | **Set** | `SISMEMBER` O(1) |
| 순 방문자 **수**만 | **HyperLogLog** | 100만 명에 **12 KB 고정** (오차 0.81%, 개별 확인 불가) |
| 출석 체크 (연속 정수 ID) | **Bitmap** | 100만 명에 125 KB |
| 유실돼도 되는 가벼운 큐 | **List** | **소비자가 꺼낸 직후 죽으면 사라진다** |
| 한 건도 잃으면 안 되는 큐 | **Stream** | 소비자 그룹 · `XACK` · `XPENDING` 재처리 |

## ④ 그래도 남는 동시성

### [분산 락과 멱등성](분산락-멱등성/분산락-멱등성.md)

**분산 락은 확률적으로 충돌을 줄이는 장치이고, 멱등성은 충돌이 일어나도 결과를 지키는 장치다.** 둘은 대체재가 아니라 **층이 다르다.**

* 서버가 한 대면 `synchronized`로 충분하다. **두 대가 되는 순간 무력해진다.** 재고 100개에 요청 200개면 락 없이는 **초과 판매 100개**가 났다.
* 핵심은 **`SET key token NX PX ttl`** 한 줄이다. `NX`가 원자적으로 한 명만 성공시키고, `PX`가 **프로세스가 죽었을 때의 영구 데드락**을 막는다. `SETNX` 후 `EXPIRE`를 따로 부르면 그 사이에 죽었을 때 **TTL 없는 락**이 남는다.
* **해제할 때 `DEL`만 하면 남의 락을 푼다.** 실측 재현했다 — A의 락이 만료돼 B가 새로 잡은 뒤 A가 `DEL`하자 **B의 락이 사라졌다.** **Lua로 토큰을 검사**해야 확인과 삭제 사이에 아무도 끼어들지 못한다.
* **토큰을 제대로 써도 TTL 문제가 남는다.** TTL 300 ms에 작업 900 ms로 재니 **임계 구역에 최대 3명이 동시에** 들어갔다. 워치독(Redisson 내장)이 대책이지만 **GC로 프로세스가 멈추면 워치독도 함께 멈춘다.**
* **그래서 분산 락은 "정확성 장치"가 아니라 "성능 최적화 장치"다.** 정확성은 **DB 유니크 제약 · 조건부 `UPDATE` · 펜싱 토큰**이 지킨다.
* **락은 비싸다.** 카운터 2,000회에서 분산 락 **186 req/s** vs `INCR` **16,479 req/s** — **89배**다. 재고 차감도 락 1,750 ms(재시도 31,221회) vs `DECR` **96 ms**였다.
* **멱등성은 락이 못 막는 것을 막는다.** 클라이언트가 타임아웃으로 재시도하면 **두 요청은 시간이 안 겹치므로 락의 범위 밖**이다. `Idempotency-Key`를 `SET NX`로 선점하니 중복 200회가 **1회 처리 / 199회 차단**이 됐다.
* **중복 요청에 오류를 주면 안 된다.** 오류를 주면 클라이언트가 또 재시도한다. **저장해 둔 같은 응답**을 돌려준다.

```text
동시성 제어 선택 순서

1순위  원자 연산          INCR · DECR · SET NX          ← 실측 96 ms
2순위  DB 락 / 조건부 UPDATE ... WHERE qty > 0          ← 트랜잭션과 생명주기가 같다
3순위  분산 락            여러 자원 · 외부 API가 얽힐 때  ← 실측 1,750 ms
그리고  멱등성 키          재시도 중복은 위 셋으로 못 막는다
```

!!! danger "네 노트가 만나는 지점"

    **`maxmemory-policy` 기본값은 `noeviction`이다.** 캐시로 쓰면서 그대로 두면 메모리가 차는 순간
    오래된 키를 버리는 게 아니라 **쓰기가 통째로 실패한다.** 캐시 갱신도, 분산 락 획득도, 멱등성 키
    선점도 전부 `SET`이라 **네 노트의 장치가 동시에 죽는다.** 캐시 용도면 `allkeys-lru`로 바꾼다.

| 락 대 원자 연산 | 186 req/s vs **16,479 req/s** — **89배** |
| 락 TTL < 작업 시간 | 임계 구역 **동시 진입 3명** · 겹친 진입 7회 |
| 중복 요청 200회 | 보호 없음 **200회 처리** · 멱등성 키 **1회 / 199회 차단** |

## 자주 틀리는 것

| 잘못된 이해 | 올바른 이해 |
| --- | --- |
| 캐시를 붙이면 무조건 빨라진다 | 원본이 캐시 왕복보다 빠르면 **손해**다. 단건 PK **54.3 µs** < Redis **540 µs**. |
| 캐시를 지우고 DB를 고치면 안전하다 | 정반대다. 그 순서가 실측 **400회 중 400회** 불일치였다. |
| 캐시는 갱신(`SET`)하는 게 효율적이다 | 두 쓰기의 순서가 뒤집히면 옛 값이 박제된다. **삭제는 멱등**이라 안전하다. |
| `@Transactional` 안에서 캐시를 지우면 된다 | **커밋 전에 지워져** 다른 요청이 옛 값을 다시 채운다. `AFTER_COMMIT`에 지운다. |
| 히트율 99%면 DB 부하는 걱정 없다 | 만료되는 **그 순간은 100% 미스**다. 실측 100개 요청이 DB를 100번 쳤다. |
| TTL을 늘리면 스탬피드가 줄어든다 | 만료 **간격**만 늘어난다. 만료되는 순간의 폭발은 똑같다. |
| Request Collapsing이면 원본 호출이 1회다 | **서버당 1회**다. 서버 10대면 10회다. |
| 논리적 만료면 아무 문제 없다 | **모두가 옛 값을 받고**(실측 100/100), **첫 진입은 못 막는다.** |
| Redis는 메모리에 있어서 빠르다 | 그보다 **자료구조가 서버에 있어 왕복과 계산을 없앤 것**이 더 크다. |
| 느린 명령은 그 요청만 느리다 | **싱글 스레드라 전부 느려진다.** 실측 다른 요청 최대 **636 ms**. |
| 원소 하나 더 넣는다고 메모리가 크게 변하진 않는다 | 임계값을 넘는 그 하나에서 **Set 18.6배, ZSet 13배**로 뛴다. |
| 메모리가 차면 오래된 키가 알아서 지워진다 | 기본이 **`noeviction`** 이라 **쓰기가 실패**한다. |
| `MULTI`는 트랜잭션이니 실패하면 롤백된다 | **롤백이 없다.** 중간 명령이 실패해도 나머지는 그대로 실행된다. |
| 분산 락을 쓰면 상호 배제가 보장된다 | TTL이 작업보다 짧자 **3명이 동시에** 들어갔다. |
| 락 해제는 `DEL`이면 된다 | 만료 뒤 **남이 잡은 락을 지운다.** Lua로 토큰을 검사한다. |
| 분산 락이 있으면 이중 결제가 안 난다 | **재시도는 시간이 안 겹쳐** 락의 범위 밖이다. **멱등성 키**가 필요하다. |
| 락을 쓰면 성능이 조금 떨어진다 | 실측 **89배**(186 vs 16,479 req/s). "조금"이 아니다. |
| 중복 요청에는 오류를 주면 된다 | 오류를 주면 **또 재시도**한다. **같은 응답**을 돌려줘야 한다. |

## 면접 직전에 이것만

!!! note "네 문장으로"

    1. **캐시는 같은 답을 두 곳에 두는 것**이라, 얻는 것은 속도고 치르는 값은 어긋남이다.
       **DB를 먼저 고치고 캐시를 지운다** — 반대 순서는 실측 400/400 영구 불일치였다.
    2. **위험한 순간은 캐시가 있을 때가 아니라 비는 순간**이다. 원본을 읽는 사람을 한 명으로 줄이거나
       (Request Collapsing, **DB 100회 → 1회**) 아예 안 기다리게 한다(논리적 만료, **p50 0 ms**).
    3. **Redis는 자료구조 서버**다. 그래서 랭킹의 "내 등수"가 4.4 µs인 대신, **싱글 스레드라
       `KEYS` 하나(158 ms)가 전체를 세운다.** 그릇을 잘못 고르면 메모리가 계단처럼 뛴다.
    4. **분산 락은 정확성 장치가 아니라 최적화 장치다.** TTL이 짧으면 3명이 들어가고 원자 연산보다
       89배 느리다. **돈이 걸린 곳은 멱등성 키와 DB 유니크 제약으로 막는다.**
