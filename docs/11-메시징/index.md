# 11. 메시징 — 한 페이지 요약

> **"지금 답에 필요 없는 일"을 큐로 넘기면 응답이 5.6배 빨라진다. 그런데 총 작업량은 그대로라 큐가 밀리고, 순서가 깨지고, 메시지가 중복되거나 사라진다. 이 섹션 셋은 그 하나의 결정과 거기서 파생된 문제들의 순서다.**

이 섹션 노트 3개의 핵심만 한 페이지로 모았다. 처음에는 지도로, 복습할 때는 체크리스트로 쓴다.
각 항목의 제목이 해당 노트 링크다. **자세한 근거와 측정 코드는 노트에 있다.**

!!! info "측정 기준"

    수치는 **JDK 21.0.12.1 (Temurin) · Windows 11 · 6코어**에서 직접 실행한 값이다. 외부 호출은
    `Thread.sleep()`으로, 건당 비용은 나노초 스핀으로 흉내 냈다. **Kafka 설정 기본값은 Apache Kafka
    4.3 공식 문서에서 확인했고**, 파티션 분포·키 이동률은 Kafka의 `Utils.murmur2`를 그대로 옮겨
    키 10만 개로 계산한 값이다 — **브로커를 띄워 잰 값이 아니므로 처리량·지연 수치는 싣지 않았다.**

## ① 왜 큐로 넘기는가

### [동기 · 비동기와 메시지 큐](동기-비동기와-메시지큐/동기-비동기와-메시지큐.md)

비동기는 "빨리 하는 것"이 아니라 **"지금 안 하는 것"** 이다.

* **동기 / 비동기**는 결과를 그 자리에서 받는가를, **블로킹 / 논블로킹**은 그동안 스레드가 붙잡히는가를 묻는다. 다른 축이다 — `Future.get()`은 비동기 API지만 그 줄에서 블로킹된다.
* 주문 저장 20 ms + 알림 3종(60 · 40 · 30)을 전부 동기로 하면 **건당 175 ms**, 알림을 큐로 넘기면 **건당 31 ms**로 **5.6배**다.
* **총 작업량 150 ms는 그대로다.** 컨슈머가 똑같이 다 처리한다. 줄어든 건 사용자가 기다리는 시간뿐이다.
* **응답 시간보다 장애 격리가 더 큰 이득**인 경우가 많다. 알림 서버가 죽어도 주문 API는 성공하고 알림만 큐에 쌓인다.
* 소비보다 생산이 빠르면 셋 중 하나는 **반드시** 버린다 — **무한 큐는 지연**(대기 평균 2,154 ms · 최대 4,660 ms), **거절은 데이터**(20,000건 중 19,000건), **차단은 상류 처리량**(생산자가 4,692 ms 정지).
* **무한 큐가 가장 위험하다.** 아무도 안 죽어서 늦게 발견되고, 결국 메모리로 터진다.
* 배치 1건 → 500건으로 바꾸면 처리량 **480 → 110,497 건/s (230배)**, 대신 배치 1회 지연 **2,005 → 4,500 µs (2.2배)**.
* 큐 하나에 컨슈머 4개를 붙이면 10,000건 중 **순서 어긋남 440건**. 키 해시로 파티션을 가르면 **0건**.
* **`@Async` 스레드풀로 충분한 경우가 많다.** 재시도와 재시작 복구가 필요 없다면 브로커를 들일 이유가 없다.

## ② 그 큐를 무엇으로 쓰는가

### [Kafka 구조와 동작](Kafka-구조와-동작/Kafka-구조와-동작.md)

Kafka는 **읽으면 사라지는 큐가 아니라 추가만 되는 로그**다. 나머지가 전부 여기서 따라 나온다.

* 소비해도 안 지워지고 **오프셋만 앞으로 간다.** 그래서 여러 그룹이 같은 데이터를 각자 읽고, 되감아 재처리할 수 있다. 사라지는 기준은 소비가 아니라 리텐션(**`log.retention.hours=168`**, 7일)이다.
* **파티션이 병렬 단위이자 순서 단위**다. 그룹 안에서 파티션 하나는 컨슈머 하나가 맡으므로, **파티션 3개에 컨슈머 5개를 띄우면 2개가 논다.**
* 키가 있는 레코드는 **`murmur2(key) & 0x7fffffff % 파티션수`** 로 간다. 키 10만 개가 파티션 8개에 **편차 +1.53%** 로 고르게 흩어졌고, 같은 키는 언제나 같은 파티션이었다.
* **파티션 증설은 되돌릴 수 없는 결정이다.** **4개 → 5개에서 80.0%**, 4 → 8은 50.1%, 8 → 12는 66.7%의 키가 이사한다. 이사한 키는 그 순간 순서 보장이 끊긴다. **줄이는 건 아예 불가능하다.**
* **`acks=all`인데도 유실된다.** `min.insync.replicas` 기본값이 **1**이라 ISR이 리더 하나로 줄어도 성공 응답이 나간다. **`replication.factor=3` + `min.insync.replicas=2`가 한 쌍**이다.
* 프로듀서 기본값은 이미 안전하다 — `acks=all` · `enable.idempotence=true` · `retries=2147483647` · `max.in.flight=5`.
* **`linger.ms` 기본값은 0이 아니라 5다** (Kafka 4.0 · KIP-1030). 기본 설정에도 최대 5 ms 배치 대기가 있다.
* 컨슈머는 두 경로로 쫓겨난다 — 하트비트 **`session.timeout.ms`(45초)**, 처리 진행 **`max.poll.interval.ms`(5분)**. 무한 리밸런싱의 범인은 보통 후자다.
* `enable.auto.commit=true`(5초)와 `auto.offset.reset=latest`가 기본값이라, **그냥 쓰면 유실되고 새 그룹은 과거를 통째로 건너뛴다.**

## ③ 넘긴 걸 어떻게 안 잃고 받는가

### [메시지 중복 · 재시도 · Outbox](메시지-중복-재시도-Outbox/메시지-중복-재시도-Outbox.md)

**"정확히 한 번"은 살 수 없는 물건이다.** 살 수 있는 건 중복이거나 유실이고, 그중 지울 수 있는 쪽을 고른다.

* 배치 100건을 받아 550번째를 처리하다 죽는 상황에서 **처리 → 커밋은 중복 50건 · 유실 0건**, **커밋 → 처리는 중복 0건 · 유실 50건**이었다. 정확히 대칭이다.
* **유실은 무엇이 사라졌는지 알 수 없어 복구가 안 된다.** 중복은 키로 판별해 버릴 수 있다. 그래서 기본은 언제나 at-least-once다.
* 같은 실측에 **멱등 컨슈머**를 붙이자 **중복 0 · 유실 0 · 실제 반영 1,000건**이 됐다. 이것이 실무에서 말하는 exactly-once다.
* 멱등성 구현은 셋 — **절대 상태 UPDATE**(그 자체로 멱등) → **조건부 UPDATE**(`WHERE status='PENDING'`, 가장 가볍다) → **처리 이력 테이블 + 유니크 제약**(가장 일반적). **업무 처리와 같은 트랜잭션**에 넣어야 한다.
* **DB 커밋과 메시지 발행은 원자적이지 않다**(이중 쓰기). 롤백 20% · 커밋-발행 사이 장애 2%로 재현하니 **발행 먼저는 유령 메시지 203건**, **커밋 먼저는 발행 유실 11건**이었다.
* **Outbox**는 발행할 메시지를 **같은 트랜잭션으로 DB에 적어** 이 문제를 없앤다 — **유령 0 · 유실 0**, 대신 릴레이 재발행으로 **중복 16건**이 남는다. **그래서 Outbox는 항상 멱등 컨슈머와 한 쌍**이다.
* **재시도는 오류를 가려서** 한다. 타임아웃 · 5xx · 데드락은 재시도, 4xx · 형식 오류 · 검증 실패는 즉시 DLQ. 영구 오류를 계속 재시도하면 **파티션 앞을 막아 뒤가 전부 멈춘다.**
* **지수 백오프만으로는 몰림이 안 풀린다.** 1,000건이 동시에 실패하면 고정 간격도 지수 백오프도 **한 100 ms 구간에 1,000건 전부**가 몰렸다. **지터를 넣자 최대 72건**, 20개 구간에 흩어졌다.
* 상한 3회 실측에서 **DLQ 101건 중 51건은 회복 가능한 일시 오류**였다. **DLQ는 쓰레기통이 아니라 대기실**이고, 되돌려 넣는 경로와 알람이 있어야 한다.

## 설정 치트시트 (Apache Kafka 4.3 기본값)

| 설정 | 기본값 | 알아 둘 것 |
| --- | --- | --- |
| `acks` | `all` | ISR **전부**이지 복제본 3대 전부가 아니다 |
| `enable.idempotence` | `true` | 재시도 중복을 브로커가 거른다 |
| `linger.ms` | **`5`** | 4.0(KIP-1030)에서 0에서 바뀌었다 |
| `batch.size` | `16384` | 차거나 `linger.ms`가 지나면 보낸다 |
| `min.insync.replicas` | **`1`** | **`2`로 바꿔야** `acks=all`이 의미를 갖는다 |
| `unclean.leader.election.enable` | `false` | 가용성보다 정합성 |
| `log.retention.hours` | `168` (7일) | 사라지는 기준은 소비가 아니라 이것 |
| `enable.auto.commit` | **`true`** (5초) | 처리 전 커밋 위험 — 보통 끈다 |
| `auto.offset.reset` | **`latest`** | 새 그룹이 과거를 건너뛴다 |
| `max.poll.records` | `500` | × 건당 처리 시간이 5분을 넘기면 리밸런싱 지옥 |
| `max.poll.interval.ms` | `300000` (5분) | 처리 진행 판정 |
| `session.timeout.ms` | `45000` (45초) | 하트비트 판정 (별도 스레드) |
| `isolation.level` | **`read_uncommitted`** | 트랜잭션을 쓰면 `read_committed`로 바꾼다 |

## 선택 기준

```text
이 일의 결과가 지금 응답에 필요한가?
├─ 예 → 동기. (결제 승인 · 재고 확인 · 로그인)
└─ 아니오
   └─ 실패 시 재시도 · 재시작 복구가 필요한가?
      ├─ 아니오 → @Async 스레드풀로 충분
      └─ 예 → 메시지 큐
         ├─ 같은 사건을 여러 시스템이 받나 / 재처리가 필요한가 → Kafka
         └─ 우선순위 · 지연 실행 · 개별 ack 가 필요한가 → RabbitMQ · SQS

이 처리가 두 번 실행되면 문제가 되는가?
├─ 아니오 → at-least-once 그대로 (로그 · 캐시 갱신)
└─ 예 → 절대 상태 UPDATE → 조건부 UPDATE → 처리 이력 테이블 순으로 검토

DB 변경과 이벤트 발행이 함께 일어나는가?
└─ 예 → Outbox (+ 멱등 컨슈머는 필수)
```

## 자주 틀리는 것

| 잘못된 이해 | 올바른 이해 |
| --- | --- |
| 비동기로 바꾸면 시스템이 빨라진다 | 총 작업량은 그대로다. 응답 시간만 175 → 31 ms. |
| 큐를 쓰면 트래픽 폭주를 견딘다 | 견디는 게 아니라 미룬다. 대기 최대 4,660 ms. |
| 큐는 순서를 보장한다 | 파티션 안에서만. 컨슈머 4개면 어긋남 440건. |
| Kafka는 읽으면 메시지가 사라진다 | 로그다. 오프셋만 움직인다. 기준은 리텐션. |
| 컨슈머를 늘리면 처리량이 는다 | 파티션 수까지만. 파티션 3에 컨슈머 5면 2개 유휴. |
| 파티션은 나중에 늘리면 된다 | 4→5에 80.0%가 이사해 순서가 끊긴다. 줄이는 건 불가능. |
| `acks=all`이면 유실이 없다 | `min.insync.replicas=1`이면 사실상 `acks=1`. |
| exactly-once 브로커를 쓰면 된다 | 브로커 안에서만. 밖으로 나가면 at-least-once + 멱등성. |
| Outbox를 쓰면 중복도 없어진다 | 유령·유실만 없앤다. 중복 16건은 멱등 컨슈머 몫. |
| 지수 백오프를 쓰면 몰림이 풀린다 | 늦출 뿐이다. 지터가 있어야 흩어진다(1,000 → 72건). |

## 면접 직전에 이것만

!!! note "세 문장으로 요약"

    **비동기는 일을 줄이는 게 아니라 응답에서 떼어 내는 것**이라, 얻는 건 응답 시간(175 → 31 ms)과
    장애 격리이고 대신 큐가 밀릴 때 지연·데이터·상류 처리량 중 하나를 반드시 내줍니다.
    **Kafka는 큐가 아니라 로그**라 되감기가 되지만 순서와 병렬성이 전부 파티션에서 나오고,
    파티션을 늘리면 실측 80%의 키가 이사해 순서가 끊기며 `acks=all`도 `min.insync.replicas=2`가
    있어야 의미가 있습니다. **배달 보장은 중복이냐 유실이냐 둘뿐**이라 지울 수 있는 중복을 고르고,
    멱등 컨슈머로 지우며, 발행과 커밋이 갈리는 문제는 Outbox로 묶습니다.
