# /study-note

대상 파일: `$ARGUMENTS` (비어 있으면 현재 IDE에서 열려 있는 `docs/` 하위의 `.md` 파일을 대상으로 한다)

내용을 이 md 파일에 막 붙여넣은 상태라고 가정하고, 아래 4단계를 순서대로 수행한다.
각 단계가 끝나면 다음 단계로 넘어가기 전에 무엇을 했는지 한두 문장으로 보고한다.

> 섹션 하나를 통째로 새로 쓰는 것이라면 `/study-note`가 아니라 **`/study-section <번호>`** 를 쓴다.

---

## 1단계 — 내용 검수 (전체적으로 맞는 내용인지 다듬기)

- 기술적으로 틀리거나 애매한 문장을 찾아 수정한다 (예: 시간/공간 복잡도 오기, 순서 오류, 근거 없는 단정).
- 같은 개념을 설명하는 문단들끼리 모순되지 않는지 확인한다.
- **문장을 다듬되 저자의 어투와 문단 길이 스타일은 유지한다.** 전체를 새로 쓰지 않는다.
- 코드 블록의 언어 태그(````java`, ````sql` 등)와 예시 코드가 실제로 컴파일/실행 가능한 수준인지 확인한다.
- **번호 매긴 질문(`1. **질문**`) 아래에 하위 불릿(`* 핵심 키워드: ...`)을 붙일 때는 반드시 4칸 들여쓰기를 쓴다.** 3칸으로 들여쓰면 mkdocs(Python-Markdown)가 순서 목록의 하위 항목으로 인식하지 못해 번호가 어긋나거나 목록이 끊긴다.

### 이 저장소의 노트는 6개 섹션을 공통으로 쓴다

```text
1. 핵심 요약 → 2. 동작 원리 → 3. 특징과 비교 → 4. 실무 주의사항 → 5. 예제 → 6. 면접 정리
```

붙여넣은 글이 이 구조가 아니면 **내용을 새로 쓰지 말고 기존 문단을 해당 섹션 아래로 옮겨서** 맞춘다. 전체 틀은 `.claude/commands/study-section.md`의 `1단계 — 노트 작성`에 있다. 특히 아래 네 가지는 비우면 안 된다.

1. **`3. 특징과 비교` 첫머리의 요약표** — `장점 / 단점 / 적합한 상황 / 주의할 상황` 4행. 검사기가 빈 칸을 오류로 잡는다.
2. **`### 30초 답변`** — 실제로 30초 안에 말할 분량. 넘치면 `#### 이어서 더 물으면`으로 내린다.
3. **`#### 답변 구조`** — 아래 8개를 고정 순서로. 정의/내부원리/장점/단점/사용상황 5개만 쓰면 면접에서 자주 나오는 "복잡도 수치", "대안과의 비교", "실무 사례"가 빠진다.
   1. **정의** — 한두 줄 핵심 정의
   2. **내부 원리** — 동작 과정을 간단히
   3. **복잡도** — 대표 시간/공간 복잡도 수치와 각각의 예시
   4. **장점**
   5. **단점**
   6. **사용 기준** — 어떤 조건에서 선택하는지
   7. **대안과 비교** — 비슷한 개념과 언제 다르게 선택하는지, 트레이드오프
   8. **실무 적용 사례** — 실제로 어디에 쓰는지 한두 줄
4. **`### 핵심 키워드`** — 인라인 코드를 ` · `로 이은 8~12개.

## 2단계 — 도식 자료 만들기

- 본문에서 그림이 있으면 이해가 확 쉬워질 지점을 1~3곳 고른다. 대개 `2. 동작 원리`와 `3. 특징과 비교`다. 흔한 후보:
  - 여러 대상의 증가/감소 추세 비교 (예: 복잡도 곡선)
  - 단계가 있는 과정 (예: 이진 탐색처럼 범위가 줄어드는 과정)
  - 구조 다이어그램 (트리, 연결 리스트, 요청 흐름 등)
- 반드시 **`scripts/svg_kit.py`를 import해서 Python으로 생성**한다 (그림판/외부 이미지 생성 금지 — 재현 가능하고 텍스트로 diff 가능해야 함). 임시 스크립트는 스크래치패드에 만들고, 결과 `.svg`만 노트와 같은 폴더에 저장한다.
- SVG 작성 규칙:
  - 배경은 밝은 카드(`#fcfcfb` 계열) + 옅은 테두리 — 다크/라이트 어느 테마에서도 안정적으로 보인다.
  - 폰트는 `system-ui, -apple-system, "Segoe UI", "Malgun Gothic", sans-serif` (외부 폰트 금지 — 오프라인·GitHub Pages 양쪽에서 깨지지 않게).
  - 계열별 색은 고정 순서로 배정하고, 색만으로 구분하지 말고 직접 라벨을 붙인다 (색약 대응).
  - **`<text>`는 연속 공백을 하나로 접는다.** 나열할 때는 ` · ` 같은 문자를 쓴다.
  - 만든 뒤 **반드시 `scripts/preview_svg.py`로 PNG 변환 후 Read 도구로 직접 눈으로 확인**한다. 라벨 겹침, 잘림, 어색한 배치가 있으면 좌표를 고쳐 다시 렌더링한다.
- 노트 본문에는 표준 마크다운 임베드로 넣는다: `![설명](파일명.svg)` — Obsidian과 GitHub Pages(mkdocs) 양쪽에서 그대로 렌더링된다. 이미지 바로 아래에 한 줄짜리 캡션(이탤릭)을 붙인다.
- 기존 문단 구조(형식)는 건드리지 않는다 — 이미지+캡션만 해당 위치에 삽입한다.

## 3단계 — 형식·배치 유지

- 노트 파일은 `docs/<NN-섹션>/<노트명>/<노트명>.md` 경로에 있어야 한다 (예: `docs/01-복잡도-자료구조/해시-트리-비교/해시-트리-비교.md`). 파일명은 폴더명과 동일하게 한다 (Obsidian 빠른 전환 시 구분을 위해 — `Main.md` 금지).
- 이미지(svg)는 노트와 **같은 폴더**에 둔다.
- `mkdocs.yml`의 `nav:`에 새 노트를 추가한다 (없으면 새 항목 만들기, 있으면 그대로 둠). 기존 항목의 순서/이름은 임의로 바꾸지 않는다.
- `docs/index.md`의 목차에서 해당 항목을 링크로 바꾼다.
- 섹션 번호와 폴더명은 `.claude/commands/study-section.md`의 **섹션 번호표**를 따른다. 새 최상위 섹션은 표에 있는 이름 그대로 만든다.

## 4단계 — GitHub Pages 배포 준비

1. `python scripts/check_notes.py <섹션>` — 6개 섹션·요약표·`면접 정리` 하위 절·들여쓰기·이미지·SVG를 한 번에 검사한다. **오류가 0이 될 때까지 고친다.**
2. `python -m mkdocs build --strict` — 깨진 링크·이미지·nav 참조 오류를 잡는다. 실패하면 원인을 고치고 다시 빌드한다.
3. (도식을 추가했다면) `mkdocs serve`로 로컬 서버를 띄우고, headless 브라우저로 실제 페이지를 스크린샷해서 레이아웃이 깨지지 않았는지 확인한다. 확인 후 서버는 반드시 종료한다.
4. `git status`로 변경 파일을 확인하고, `git diff`로 의도치 않은 변경(예: `.obsidian/workspace.json`, `site/` 폴더)이 섞이지 않았는지 점검한다.
5. 변경 요약(새/수정된 파일 목록, 추가한 도식 설명)을 사용자에게 보여주고 **커밋/푸시 여부를 확인받는다.** 확인 전에는 push하지 않는다.

### 참고: SVG 미리보기 렌더링

```
python scripts/preview_svg.py "docs/경로/파일.svg"
```
같은 폴더에 `파일.preview.png`가 생성된다. Read 도구로 열어 확인한 뒤, 확인용 PNG는 커밋하지 않는다.
