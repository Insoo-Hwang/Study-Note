# /study-work

정리할 내용: `$ARGUMENTS`

`/study-section`이 **면접 커리큘럼(01~12)** 을 6개 섹션 형식으로 만드는 명령이고
`/study-infra`가 **설치·설정한 환경**을 남기는 명령이라면,
이 명령은 **업무에서 쓰는 기술 스택을 파고든 기록(`docs/work/`)** 을 다룬다.

**형식은 고정이다.** 붙여넣은 내용을 **`## 개념 설명`과 `## 면접 질문` 둘로 갈라** 쓴다.
공부한 것과 그것을 말로 뱉는 연습은 읽는 목적이 다르다. 한 문서 안에 섞여 있으면
복습할 때 매번 다시 분류해야 해서, 처음 쓸 때 한 번 갈라 두는 편이 싸다.

> 트리를 나눠 둔 이유와 검사 규칙은 `docs/work/index.md`에 있다. 시작 전에 한 번 읽는다.

# 3. JPA N+1과 페치 조인

> **컬렉션 페치 조인은 페이징과 같이 쓸 수 없고, 그 자리는 `@BatchSize`가 대신한다.**

`Spring Boot 3.3.4` · `Hibernate 6.5` · MySQL 8.0

## 개념 설명

### 왜 팠는가
주문 목록 API가 느려서 로그를 봤더니 목록 쿼리 하나에 상세 쿼리가 100개 더 나가고 있었다.

### N+1이 생기는 자리
지연 로딩된 연관을 실제로 건드리는 순간 초기화 쿼리가 하나씩 나간다.

```sql
select o1_0.id, o1_0.name from orders o1_0            -- 1번
select i1_0.id from order_item i1_0 where i1_0.order_id = ?   -- N번
```

### 페치 조인과 페이징을 같이 못 쓰는 이유
조인 결과가 부풀어 DB에서 자를 행 수를 셀 수 없다. Hibernate는 전부 읽어 메모리에서 자른다.

```text
HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory
```

### 우리 코드에서는
목록 조회는 `@BatchSize(size = 100)`로 두고, 단건 상세만 페치 조인을 쓴다.

## 면접 질문

### Q1. JPA에서 N+1 문제가 무엇인가요?
**목록 하나를 조회한 뒤 연관 엔티티를 건드릴 때마다 조회 쿼리가 한 번씩 더 나가는 것입니다.**

주문 100건을 조회하면 목록 쿼리 1번에 주문 항목 조회 100번이 더 나갑니다.
지연 로딩 자체가 문제는 아니고, 프록시를 실제로 건드리는 코드가 반복문 안에 있을 때 드러납니다.

### Q2. 페치 조인으로 풀 때 주의할 점은요?
**컬렉션 페치 조인은 페이징과 같이 쓸 수 없습니다.**

조인 때문에 행이 부풀어서 DB가 몇 행을 잘라야 할지 알 수 없습니다. Hibernate는 경고
`HHH90003004`를 남기고 전체를 읽어 메모리에서 자르기 때문에, 데이터가 커지면 그대로 터집니다.

### Q3. 그러면 페이징이 필요할 때는 어떻게 하나요?
**컬렉션은 페치 조인 대신 `@BatchSize`로 IN 절 묶음 조회를 씁니다.**

부모만 페이징으로 가져오고, 자식은 배치 크기만큼 `in (?, ?, …)`으로 모아 읽습니다.
쿼리 수가 N에서 N/배치크기로 줄고 페이징도 DB에서 그대로 됩니다.

## 참고
- [Hibernate 6.5 — Fetching](https://docs.jboss.org/hibernate/orm/6.5/userguide/html_single/Hibernate_User_Guide.html#fetching)

## 0단계 — 입력 해석과 대상 정하기

### 입력을 어디서 읽는가

| `$ARGUMENTS` | 처리 |
| -- | -- |
| 노트 내용 (여러 줄) | 그대로 정리 대상으로 삼는다 |
| 파일 경로 하나 | 그 파일을 읽어 정리 대상으로 삼는다 |
| 짧은 주제어 하나 (`JPA N+1`) | 아래 **내용이 없을 때** 를 따른다 |
| 비어 있음 | 현재 IDE에서 열려 있는 `docs/work/` 하위 `.md`를 대상으로 삼는다. 그것도 없으면 아래를 따른다 |

**내용이 없을 때** — 지어내지 않는다. 주제어만 받고 일반론을 채워 넣으면 그건 실무 노트가 아니라
커리큘럼 노트의 열화판이다. 무엇을 겪었는지(어떤 코드에서, 어떤 증상으로, 어느 버전에서)를
물어보고 멈춘다.

> **질문·답변이 비어 있는 것은 물어볼 일이 아니다.** 개념 내용만 있으면 그대로 진행하고
> 면접 질문 절은 직접 만든다. 되묻는 것은 *개념 내용 자체가* 없을 때뿐이다.

### 이 트리가 맞는가

먼저 **어느 트리에 갈 내용인지** 판단한다. 주인공이 무엇이냐로 가른다.

| 주인공 | 갈 곳 |
| -- | -- |
| 어디서든 통하는 개념 일반론 | `/study-section` (커리큘럼 01~12) |
| 설치 · 설정 · 서버 · 컨테이너 · 네트워크 · CI/CD | `/study-infra` |
| 애플리케이션 코드 · API · 라이브러리 · 프레임워크 내부 | **여기** |

다른 트리가 맞다고 판단되면 **그 이유와 함께 해당 명령을 안내하고 멈춘다.**
애매하면 여기에 쓰고, 나중에 옮기면 된다고 알린다 (폴더 이동 + 등록 두 줄이 전부다).

### 새 노트인가, 기존 노트에 합칠 것인가

`docs/work/` 아래 폴더 목록과 `docs/work/index.md`의 노트 목록을 먼저 읽는다.

- **같은 주제 노트가 이미 있으면 새로 만들지 않고 합친다.** `JPA-N+1과-페치조인` 노트가 있는데
  `@BatchSize` 이야기를 또 가져왔다면 새 노트가 아니라 그 노트의 보강이다.
- 주제가 뚜렷이 다르면 새 노트를 만든다.
- **애매하면 그때만 물어본다.** 판단이 서면 어느 쪽으로 정했는지 한 줄로 알리고 그대로 진행한다.

합칠 때는 **두 섹션 각각에 나눠 넣는다.** 새로 안 개념은 `## 개념 설명` 아래 `###` 절로,
새로 만든 질문은 `## 면접 질문` 끝에 다음 번호로 잇는다. **대섹션을 새로 만들지 않는다** —
`##`는 이 노트에 셋(`개념 설명` · `면접 질문` · `참고`)뿐이고 검사기가 그 밖을 잡는다.

기존 문단은 지우지 않는다. 기존 내용과 충돌하면(예전에 A라고 썼는데 이번에 B가 맞다고 확인됨)
지우지 말고 `~~A~~ → B (2026-08 재확인, Hibernate 6.5)` 처럼 **바뀐 사실과 시점을 남긴다.**
라이브러리는 메이저 버전이 오르며 기본 동작이 바뀌는 일이 잦아서, 바뀌었다는 사실 자체가 정보다.

### 커리큘럼 노트와 겹칠 때

같은 기술이 커리큘럼에도 있으면(JPA는 `07-트랜잭션-데이터접근`, Redis는 `08-캐시-Redis`)
**커리큘럼 노트를 고치지 말고 링크한다.** 링크는 `## 개념 설명` 첫머리에 둔다.

```markdown
> 일반론은 [JDBC · MyBatis · JPA](../../07-트랜잭션-데이터접근/JDBC-MyBatis-JPA/JDBC-MyBatis-JPA.md)에 있다.
> 여기서는 우리 코드에서 실제로 터진 것만 본다.
```

- 커리큘럼 노트는 6개 섹션 검사를 받는 문서라 **여기서 건드리면 검사가 깨질 수 있다.**
- 링크는 `docs/work/<노트명>/`에서 출발하는 상대 경로다 (`../../`로 두 단계 올라간다).
- 반대로 커리큘럼 노트에서 이 트리로 링크를 거는 것은 하지 않는다 — 커리큘럼은 그 문서 하나로
  완결되어야 한다.

### 제목 — `O주차 학습 :` 을 떼고 `O.` 로 바꾼다

붙여넣는 글의 첫 줄은 보통 `3주차 학습 : JPA N+1과 페치 조인` 꼴로 들어온다.
**`주차 학습` 같은 껍데기는 제목에 남기지 않는다.** 주차 번호만 살려 `N.` 으로 앞에 붙인다.

| 들어온 첫 줄 | 노트 제목(`# `) | 폴더 · 파일명 |
| -- | -- | -- |
| `3주차 학습 : JPA N+1과 페치 조인` | `# 3. JPA N+1과 페치 조인` | `03-JPA-N+1과-페치조인` |
| `3주차 학습: Bean 생명주기와 자동설정` | `# 3. Bean 생명주기와 자동설정` | `03-Bean-생명주기와-자동설정` |
| `12주차 학습 - Kafka 컨슈머 설정` | `# 12. Kafka 컨슈머 설정` | `12-Kafka-컨슈머-설정` |
| 주차 표기가 없는 글 | `# JPA N+1과 페치 조인` | `JPA-N+1과-페치조인` |

- **제목의 번호는 `N.` — 점 하나에 공백 하나.** 자릿수를 채우지 않는다 (`3.` 이지 `03.` 이 아니다).
- **폴더·파일명의 번호는 두 자리로 채운다** (`03-`). 파일 목록이 주차 순으로 정렬되게 하려는 것이라
  제목과 규칙이 다르다.
- **`주차`·`학습`·`정리` 같은 말은 제목에서 지운다.** 무엇을 팠는지가 제목이어야 검색이 된다.
  검사기가 제목에 `주차`가 남아 있으면 오류로 잡는다.
- 한 주에 노트를 여러 개 쓰면 번호가 겹쳐도 된다. 뒤의 주제어가 다르니 폴더는 안 겹친다.
- `mkdocs.yml` nav 라벨과 `docs/work/index.md` 링크 제목도 **`# ` 제목과 똑같이** 적는다
  (`3. JPA N+1과 페치 조인`).

### 경로와 이름

```text
docs/work/<노트명>/<노트명>.md
docs/work/<노트명>/<도식>.svg
```

- **폴더명 == 파일명.** 검사기가 잡는다.
- **공백 대신 하이픈.** 조사는 빼고 핵심어만 남겨 짧게 (`JPA에서 N+1 문제 해결하기` → `JPA-N+1과-페치조인`).
- **카테고리 폴더를 더 파지 않는다.** `docs/work/jpa/n+1/…` 처럼 한 단계 더 들어가면
  검사기 glob(`docs/*/*/*.md`)에서 빠져 아무 검사도 받지 않는다.
  데이터 접근·메시징·프레임워크 같은 묶음은 **`mkdocs.yml`의 nav에서** 중첩으로 만든다.

### `## 개념 설명` — 붙여넣은 글을 대하는 태도

**전체를 새로 쓰지 않는다.** 사용자가 직접 부딪히고 적은 것이 원본이고, 그 어투와 문단 길이를 유지한다.
하는 일은 세 가지다.

1. **틀린 것을 고친다** (2단계에서 실제로 확인한다)
2. **빠진 맥락을 채운다** — 아래 세 가지는 나중의 내가 반드시 아쉬워한다
3. **다시 찾아볼 수 있게 `###` 절로 나눈다** — 뒤섞인 메모에 제목을 붙인다

| 빠지면 생기는 일 | 채울 것 |
| -- | -- |
| 이 동작이 지금도 맞나? | **버전** — `Spring Boot 3.3.4` · `Hibernate 6.5` · MySQL 8.0. 노트 맨 위에 적는다 |
| 이걸 왜 팠더라? | **계기** — `### 왜 팠는가`에 한 줄 |
| 그래서 어떻게 하라는 거지? | **결론** — `### 우리 코드에서는`에 지금 우리 코드에서 무엇을 어떻게 쓰기로 했는지 |

다 파지 못한 것은 파다 만 채로 남긴다. 안 남기고 다음에 처음부터 다시 파는 것보다 낫다.
다만 **확인 못 한 것을 그대로 적어 두지는 않는다** — 2단계에서 문서를 찾아보고, 그래도 안 나오면 지운다.
정말로 답이 없는 열린 질문만 `### 아직 못 본 것` 처럼 `개념 설명` 안쪽 절에 남긴다.

### `## 면접 질문` — 질문도 답변도 이 명령이 만든다

사용자가 붙여넣은 글에는 보통 질문도 답도 없다. **비어 있다고 비워 두지 않는다.**
`## 개념 설명`을 다 쓴 뒤, 그 내용에서 면접관이 물을 만한 것을 뽑아 질문과 답을 직접 쓴다.

만드는 순서는 이렇다.

1. 개념 설명의 `###` 절을 훑어 **면접에서 실제로 물을 지점**을 고른다 — 정의, 동작 원리,
   트레이드오프, 실패 사례, 대안 비교. 절 하나가 질문 하나가 되는 것이 보통이다.
2. 각 지점을 **면접관의 말투로** 한 문장 질문으로 세운다.
3. **굵은 글씨 한 줄 답**을 먼저 쓰고, 그 아래에 근거·예시를 2~4문장 붙인다.
4. 뻔히 이어질 꼬리질문이 있으면 그것도 `Q`로 세운다.

지킬 것.

- **질문은 실제로 나올 문장으로.** `영속성 컨텍스트` 같은 명사가 아니라
  `Q1. 트랜잭션 안에서 엔티티를 수정하면 update 쿼리가 언제 나가나요?` 처럼 쓴다.
- **답은 굵은 글씨 한 줄로 시작한다.** 훑을 때 이 줄만 읽는다. 검사기가 이 줄을 본다.
- **답변 본문은 말하는 순서로.** 결론 → 근거 → 예시. 표와 코드 나열이 아니라 문장이다.
  실제로 소리 내 읽어서 30초 안에 끝나는 길이면 적당하다.
- **개념 설명을 문장째 복사하지 않는다.** 같은 사실을 말로 뱉는 형태로 다시 짠다.
  복사본이 될 바에는 질문을 빼는 편이 낫다.
- **답에 새 사실이 나오면 그것을 개념 설명에 먼저 넣는다.** 두 절이 서로 다른 말을 하면 안 된다.
  새로 넣은 사실도 2단계 검증 대상이다.
- 질문 수는 내용에 맞춘다. 보통 **3~6개.** 억지로 채우지 않는다.
- 사용자가 붙여넣은 글에 이미 질문이 있으면 **그 질문을 살리고 답만 채운다.**
  질문 문장을 임의로 다듬지 않는다 — 사용자가 실제로 들은 질문일 수 있다.

### 지켜야 하는 것 (검사기가 잡는다)

- **`## 개념 설명` → `## 면접 질문` 순서로 하나씩.** 그 밖의 `##`는 `## 참고`만 허용
- **질문 제목은 `### Q1. <질문>` 꼴, 1부터 순서대로**
- **각 질문 아래 첫 줄은 굵은 글씨 한 줄 답**
- **`# ` 제목에 `주차`·`학습` 같은 껍데기가 남아 있지 않을 것** (`# 3. 주제명`)
- **파일명 == 폴더명**
- **번호 목록 아래 하위 불릿은 4칸 들여쓰기** — 3칸이면 mkdocs에서 목록이 끊긴다
- **참조한 이미지가 같은 폴더에 실제로 있을 것.** 외부 이미지(`https://…`) 금지
- **SVG는 XML로 파싱될 것.** 외부 리소스 참조 금지

코드 블록 언어 태그(` ```java `, ` ```sql `, ` ```yaml `)도 붙인다 — 없으면 경고가 뜬다.
로그·스택트레이스처럼 언어가 없는 출력은 ` ```text `를 쓴다.

### 공개 저장소다 — 사내 코드를 그대로 옮기지 않는다

이 저장소는 **GitHub Pages로 공개 배포된다** (`https://Insoo-Hwang.github.io/Study-Note/`).
실무 노트는 세 트리 중 이 위험이 가장 크다. 회사 코드·스키마·설정을 붙여넣으면 그대로 공개된다.

**원칙: 사내 코드를 옮기지 말고, 같은 현상을 재현하는 최소 예제로 바꿔 쓴다.**
`OrderSettlementBatchService`를 `OrderService`로, 사내 도메인을 주문·상품 같은 일반적인 예로
바꾸면 노트의 가치는 그대로면서 회사 것은 남지 않는다. **작성 전에 훑고 치환한다.**

| 지울 것 | 바꿔 쓸 것 |
| -- | -- |
| 사내 클래스 · 패키지 · 테이블 · 컬럼 이름 | 일반적인 도메인 이름 (`com.example.order`) |
| 사내 API 엔드포인트 · 내부 도메인 · 호스트명 | `https://api.example.com` |
| 토큰 · API 키 · 비밀번호 · `.env` 값 | `<TOKEN>` · `${DB_PASSWORD}` |
| 실제 데이터 · 고객 정보가 든 로그 | 형태만 남긴 더미 값 |
| 공인 IP · 서버 IP | `203.0.113.10` (문서용 대역) |
| 사내 위키 · 지라 · MR 링크 | 지우거나 공개 문서 링크로 대체 |
| 실명 · 계정 ID가 박힌 경로 | `/home/user/...` |

**한 번 커밋해서 푸시하면 지워도 히스토리에 남는다.** 커밋 전에 잡는 것이 유일한 기회다.
지운 자리에는 `<TOKEN>`처럼 **무엇이 들어갈 자리인지** 남겨 둔다.

> 치환하다 노트의 요점이 사라질 것 같으면(사내 구조 자체가 설명의 핵심인 경우) **쓰지 말고
> 사용자에게 알린다.** 공개 저장소에 올릴 수 없는 내용은 여기 있을 자리가 아니다.

## 2단계 — 사실 검증 (건너뛰지 않는다)

라이브러리 동작을 기억으로 쓰면 거의 틀린다. 기본값 하나, 애노테이션 속성 하나가 버전에 따라 바뀐다.
**노트에 적은 동작은 실제로 돌려서 확인한다.**

**면접 질문의 답도 똑같이 검증한다.** 이 절은 이 명령이 직접 쓴 문장이라 검증을 건너뛰기 쉬운데,
틀린 답을 외우는 것은 안 외우는 것보다 나쁘다.

먼저 버전을 확정하고 노트 맨 위에 적는다.

```bash
./gradlew dependencies --configuration runtimeClasspath | head -40
./gradlew -q dependencyInsight --dependency hibernate-core --configuration runtimeClasspath
# Maven이면
./mvnw dependency:tree
```

특히 아래는 반드시 실측한다.

- **기본값** — `@Transactional`의 전파·격리, `max.poll.records`, 커넥션 풀 크기, 타임아웃.
  "기본이 30초"류는 공식 문서에서 확인하거나 직접 조회한다.
- **실제로 나가는 쿼리와 호출** — N+1이든 플러시 시점이든, 로그로 **보여준다.**
  추측한 쿼리를 적으면 나중에 다른 문제로 착각한다.
- **애노테이션·옵션이 지금 버전에 있는지** — 이름이 바뀌거나 deprecated 된 것이 가장 흔하다.
- **예외 메시지** — 그대로 붙인다. 이게 나중에 검색어가 된다.

검증용 프로젝트·설정은 **스크래치패드**에 만들고, 확인이 끝나면 정리한다.
사용자의 프로젝트에서 실험하지 않는다.

> **환경을 바꾸는 명령은 먼저 확인받는다.** 조회(`dependencies`, `--version`, 로그 읽기)는
> 그냥 실행하되, 사용자 프로젝트의 상태를 바꾸는 것(빌드 파일 수정, 마이그레이션 실행,
> DB 스키마 변경, 포트 점유)은 무엇을 왜 실행하는지 말하고 승인받는다.

### 직접 못 돌린 것은 공식 문서를 찾아본다 — 그래도 안 나오면 지운다

노트에 `(미검증)` 딱지를 남기지 않는다. 반쯤 믿는 문장은 반쯤 쓸모없고, 나중에는 결국 그냥 믿게 된다.
직접 실행으로 확인이 안 되면 **순서대로** 처리한다.

1. **공식 문서·릴리스 노트·소스에서 찾는다.** WebSearch·WebFetch로 그 버전의 레퍼런스,
   릴리스 노트, javadoc, GitHub 이슈를 본다. 아티팩트를 직접 열어 보는 것도 확인이다
   (`unzip -p <jar> META-INF/...`, POM에서 플러그인 설정 확인).
2. **찾았으면 근거를 문장에 박고 `## 참고`에 링크를 남긴다.** 원문 표현을 짧게 인용하면 더 좋다
   (`"Configures any JavaCompile tasks to use the -parameters compiler argument"`).
   출처가 있으면 그것도 검증이므로 딱지를 붙이지 않는다.
3. **그래도 확인이 안 되면 그 문장을 노트에서 지운다.** 아깝다고 남기지 않는다.
   지웠다는 사실은 노트가 아니라 **6단계 보고**에서 사용자에게 알린다.

`### 아직 못 본 것` 같은 절도 같은 기준으로 다룬다. 검색해도 답이 없는 열린 질문만 남기고,
문서에 답이 있는 항목은 본문으로 올리거나 지운다.

검증에서 틀린 내용을 찾으면 **개념 설명과 면접 질문 양쪽을 다 고친다.** 한쪽만 고치면
두 절이 서로 다른 말을 하는 문서가 된다.

## 3단계 — 도식 (필요할 때만)

실무 노트에서 그림이 값을 하는 자리는 대체로 **시간 순서**와 **객체 관계**다.
도식은 `## 개념 설명` 안에 둔다. 면접 질문 절은 글로만 간다 — 말로 답하는 연습이라 그림이 없다.

- 시점 다이어그램 (영속성 컨텍스트 → 플러시 → 커밋, 락 획득 → 만료 → 갱신)
- 요청 하나가 지나가는 계층 (Controller → Service → Repository → DB)
- 객체·엔티티 관계와 그 관계에서 생기는 쿼리
- 재시도·예외 처리 분기

만드는 규칙은 커리큘럼 노트와 **완전히 같다.** 트리가 달라도 도식 스타일은 하나로 간다.

- **`scripts/svg_kit.py`를 import해서 Python으로 생성한다.** 그림판·외부 이미지 생성 금지 —
  재현 가능하고 텍스트로 diff 되어야 한다. 주로 쓰는 것은
  `head()` · `cell()` · `band()` · `arrow()` · `line()` · `txt()` · `circle()` · `save()`다.
- 생성 스크립트는 **스크래치패드**에 두고 결과 `.svg`만 노트와 같은 폴더에 저장한다.
- **색만으로 구분하지 말고 라벨을 직접 붙인다** (색약 대응).
- **`<text>`는 연속 공백을 하나로 접는다.** 나열은 ` · `나 ` / `로 잇는다.
- **`band()`는 label을 `y+21`, sub를 `y+38`에 그린다.** 높이를 46보다 작게 주면 sub가 카드 밖으로 나간다.

만든 뒤 **반드시 눈으로 확인한다.**

```bash
python scripts/preview_svg.py "docs/work/<노트명>/<파일>.svg"
```

생성된 `*.preview.png`를 Read 도구로 열어 라벨 겹침·잘림·어색한 배치를 본다.
본문에는 표준 마크다운으로 넣고 **바로 아래에 이탤릭 캡션 한 줄**을 붙인다.

```markdown
![무엇을 보여주는 그림인지](파일명.svg)

*그림이 말하는 결론 한 줄.*
```

## 4단계 — 등록 (두 곳뿐)

### 1. `docs/work/index.md`의 노트 목록

```markdown
- [3. JPA N+1과 페치 조인](03-JPA-N+1과-페치조인/03-JPA-N+1과-페치조인.md) — 왜 우리 코드에서만
  `@EntityGraph`로 안 풀렸는지
```

- 링크는 **`docs/work/` 기준 상대 경로**다. 검사기가 이 경로로 등록 여부를 본다.
- 첫 노트를 추가할 때는 `아직 작성한 노트가 없다` 문단을 **지우고** 실제 목록으로 바꾼다.
- **링크 제목은 노트의 `# ` 제목 그대로** 쓴다 (`3. JPA N+1과 페치 조인`).
- 제목 뒤에 **`— 한 줄 설명`을 붙인다.** 노트 제목만으로는 뭘 팠는지 기억나지 않는다.
- **주차 번호 순으로 나열한다.** 카테고리로 묶지 않는다 — 이 트리는 주차 순서가 곧 목차다.

### 2. `mkdocs.yml`의 `실무 노트` 그룹

```yaml
  - 실무 노트:
      - work/index.md                    # ← 라벨 없이. 이 줄을 항상 첫 줄로 유지한다
      - 3. JPA N+1과 페치 조인: work/03-JPA-N+1과-페치조인/03-JPA-N+1과-페치조인.md
```

- **`실무 노트`는 최상위 항목 그대로, 그리고 세 번째 자리에 둔다.** 최상위 항목은
  `CS 노트` · `인프라 노트` · `실무 노트` 셋이고 Material의 `navigation.tabs`가 이 셋을
  헤더의 탭 — 즉 모드 전환 버튼 — 으로 그린다.
- **순서를 바꾸거나 사이에 항목을 끼우지 않는다.** `docs/stylesheets/mode.css`가 모드별 색을
  탭 순서(`nth-child(2)` 인프라 / `nth-child(3)` 실무)로 판별하기 때문에, 순서가 바뀌면
  헤더 색이 엉뚱한 모드에 붙는다. 정말 바꿔야 한다면 mode.css도 같이 고친다.
- **`work/index.md`를 첫 줄에서 밀어내지 않는다.** 그 자리를 뺏으면 `실무 노트` 탭이
  링크가 아니라 그냥 펼침 토글이 된다 (Material의 `navigation.indexes`).
- **새 노트는 주차 번호 순으로 이 그룹 끝에 잇는다.** 중간 폴더를 만들지 않는다.
- **01~12 커리큘럼 항목과 `인프라 노트` 그룹은 건드리지 않는다.**

### 넣지 않는 곳

- `docs/index.md` (커리큘럼 목차)
- `docs/infra/index.md` (인프라 트리 목차)
- `README.md`의 커리큘럼 트리와 진행률 표(`작성 완료 N개 / 전체 51개`)

**세 트리를 갈라 둔 이유가 이것이다.** 실무 노트는 51개 집계에 들어가지 않는다.
(`README.md`의 `# 커리큘럼 밖 노트 (인프라 · 실무)` 절은 규칙 설명이라 노트마다 고칠 필요 없다.)

2. `git status`로 변경 파일을 확인하고 `site/`·`.obsidian/`이 섞이지 않았는지 본다.
3. **`git diff`로 사내 정보가 남지 않았는지 마지막으로 훑는다** (1단계의 표).
   클래스명·테이블명·호스트명까지 본다. 커밋 전이 마지막 기회다.
4. 사용자에게 보고한다.
    - 새로 만든 노트인지 기존 노트에 합친 것인지, 그 판단 근거
    - **직접 세운 질문 목록** — `Q1. …` 한 줄씩. 사용자가 만들지 않은 부분이라 눈으로 봐야 한다
    - **2단계에서 확인한 것과 고친 것** — 버전·기본값·실제 동작이 적힌 것과 달랐던 부분
    - **직접 못 돌려서 공식 문서로 확인한 것**과 그 출처
    - **확인이 안 돼서 노트에서 지운 문장** — 지운 사실은 노트에 안 남으니 여기서 반드시 말한다
    - 사내 정보라서 일반적인 이름으로 치환한 것
    - 추가한 도식과 각각이 보여주는 것
    - 검사·빌드 통과 여부
5. **커밋/푸시 여부를 확인받는다. 확인 전에는 커밋도 푸시도 하지 않는다.**

```bash
git add docs/work mkdocs.yml
git commit -F <메시지파일>      # 여러 줄이면 파일로 넘긴다
```
