# /study-section

대상 섹션: `$ARGUMENTS`

`/study-note`가 **이미 붙여넣은 노트 하나**를 다듬는 명령이라면, 이 명령은 **섹션 하나를 처음부터 끝까지 만드는** 명령이다.

---

## 0단계 — 섹션 해석과 범위 확정

`$ARGUMENTS`는 아래를 전부 같은 섹션으로 해석한다. 사용자에게 형식을 되묻지 않는다.

```
03-알고리즘   03 알고리즘   03알고리즘   03   알고리즘
```

해석 규칙:

1. 숫자만 있으면 `docs/NN-*` 폴더에서 번호가 일치하는 것을 찾는다.
2. 이름만 있으면 폴더명 뒷부분이 일치하는 것을 찾는다.
3. 둘 다 있으면 그대로 `docs/NN-이름` 을 쓴다.
4. **비어 있으면** `docs/index.md`에서 **링크가 하나도 없는 가장 앞 섹션**을 고르고, 어느 섹션을 할지 한 줄로 알린 뒤 그대로 진행한다.

그다음 `docs/index.md`에서 해당 섹션의 항목을 읽는다.

- 이미 `[...](...)` 링크가 걸린 항목 = 완료 → 제외
- 링크 없는 텍스트 항목 = 이번에 쓸 대상

**대상 목록을 한 번 보여준 뒤 곧바로 1단계로 넘어간다. 몇 개를 할지 사용자에게 묻지 않는다.**
(섹션당 항목이 3개 안팎이라 한 번에 처리 가능하다. 예외적으로 대상이 5개를 넘으면 그때만 나눠서 할지 물어본다.)

## 1단계 — 노트 작성

### 경로와 이름

```
docs/<NN-섹션>/<노트명>/<노트명>.md
```

- **폴더명·파일명은 동일**하게 한다 (`Main.md` 금지).
- **공백 대신 하이픈**을 쓴다. 목차에 적힌 이름을 그대로 쓰되 공백만 `-`로 바꾼다.
  - `탐색과 정렬` → `docs/03-알고리즘/탐색-정렬/탐색-정렬.md`
  - `Heap과 PriorityQueue` → `docs/02-자료구조/Heap-PriorityQueue/Heap-PriorityQueue.md`
  - `낙관적 락 · 비관적 락` → `docs/07-트랜잭션/낙관적-비관적-락/낙관적-비관적-락.md`
- 조사(`과`, `와`, `·`)는 빼고 핵심어만 남겨 짧게 만든다. 확정한 폴더명을 목차 링크와 `nav`에 그대로 쓴다.

### 이 저장소의 노트는 "묶음 비교 노트"다

목차 항목 하나가 **여러 키워드를 묶은** 형태다 (`탐색과 정렬` = 선형 탐색 + 이진 탐색 + 정렬 + `Comparable`/`Comparator`).

따라서 16개 섹션은 그대로 유지하되, 내용이 많은 섹션은 **키워드별 `###` 하위 절로 나눈다.**

```markdown
## 6. 성능 특성

### 선형 탐색
...
### 이진 탐색
...
### 정렬
...
```

각 키워드를 따로 설명만 하고 끝내지 말고, **언제 무엇을 고르는지 비교하는 문단을 반드시 넣는다.** 묶어 놓은 이유가 그것이다.

### 16개 섹션 (이 순서, 비우지 않는다)

```
1. 핵심 요약        2. 등장 배경       3. 핵심 개념        4. 구조와 동작 원리
5. 코드 또는 사용 예시  6. 성능 특성      7. 장점과 단점       8. 사용 기준
9. 비슷한 개념 비교   10. 백엔드 실무 적용  11. 자주 하는 오해    12. 면접 답변
13. 예상 면접 질문   14. 추가 학습 방향   15. 최종 체크리스트   16. 한 줄 결론
```

### 작성 규칙 — 전부 실제로 문제가 됐던 것들이다

- **`2. 등장 배경`은 "무엇"이 아니라 "왜"를 쓴다.** 이 개념이 없을 때 어떤 코드를 직접 써야 하는지 보여주면 필요성이 분명해진다.
- **`### 답변 구조`는 아래 8개를 고정 순서로 채운다.** 번호 목록(`1. **정의** — ...`) 형식을 쓴다.
  ```
  1. **정의**   2. **내부 원리**   3. **복잡도**   4. **장점**
  5. **단점**   6. **사용 기준**   7. **대안과 비교**   8. **실무 적용 사례**
  ```
  정의/내부원리/장점/단점/사용상황 5개만 쓰면 면접에서 자주 나오는 복잡도 수치·대안 비교·실무 사례가 빠진다.
- **번호 매긴 항목 아래 하위 불릿은 4칸 들여쓰기.** 3칸이면 Python-Markdown이 순서 목록의 하위 항목으로 인식하지 못해 번호가 끊긴다.
- 코드는 **정통 Java**로 쓴다 (람다·스트림·병렬 처리 금지). 코드 블록에는 언어 태그를 붙인다.
- 텍스트 도식(```text 블록)과 표를 적극적으로 쓴다.
- 같은 내용을 여러 섹션에서 반복하지 않는다.

## 2단계 — 사실 검증 (건너뛰지 않는다)

노트를 다 쓴 뒤, **버전에 따라 달라지거나 수치가 들어간 주장은 직접 실행해서 확인한다.** 기억에 의존하면 틀린다.

```bash
java -version    # 먼저 대상 JDK 버전을 확인한다
```

임시 검증 코드는 스크래치패드에 만들고 단일 파일 실행(`java Verify.java`)으로 돌린다. 내부 필드는 리플렉션으로 본다.

```bash
java --add-opens java.base/java.util=ALL-UNNAMED Verify.java
```

특히 다음은 반드시 실측한다.

- 내부 배열의 **초기 용량과 증가 규칙**, 임계값·로드 팩터 같은 **상수**
- **성능 비교 수치** (O(n²) vs O(n) 같은 주장은 실제로 재서 배수를 적는다)
- 컬렉션의 **순회 순서**, 예외 종류 (`NullPointerException` vs `UnsupportedOperationException` 등)
- **한계값** (재귀 깊이, 오버플로가 실제로 일어나는 지점)

> 실제로 잡아낸 사례
>
> - `ArrayDeque`의 "용량은 2의 거듭제곱" 설명은 **Java 8까지만** 맞다. Java 9부터 제약이 사라져 JDK 17 실측 기본 용량은 **17**이고 `17 → 36 → 74 → 111`로 늘어난다.
> - `DualPivotQuicksort`의 임계값 47·286은 **JDK 13 이전** 값이다. JDK 14에서 전면 재작성되어 JDK 17 실측값은 **44·65**다.
> - 재귀 깊이 한계는 고정값이 아니다. `-Xss`에 정비례하고(256k→5,278 / 8m→208,450), 프레임 크기에 반비례하며, **같은 코드도 실행마다 다르다**(23,408과 24,960).
> - `int` 누적 오버플로는 **음수가 아니라 그럴듯한 양수**가 된다(10만×100만 → `1,215,752,192`). "음수면 검사하면 된다"가 안 통한다.
>
> 버전에 따라 다른 내용은 지우지 말고 **"Java 8까지는 A, Java 9부터는 B"** 로 함께 적는다. 면접에서 오히려 강점이 된다.

검증 결과 틀린 내용을 찾으면 노트 전체(핵심 요약·본문·오해 표·면접 답변·예상 질문)에서 **빠짐없이** 고친다. 한 곳만 고치면 문서 안에서 모순이 생긴다.

## 3단계 — 도식 만들기

노트마다 그림이 있으면 이해가 확 쉬워지는 지점을 **1~3곳** 고른다. 좋은 후보는 단계가 있는 과정, 구조 다이어그램, 두 방식의 대비, 실측 수치 막대그래프다.

- 반드시 **`scripts/svg_kit.py`를 import해서 Python으로 생성한다.** 스타일(색·폰트·카드 배경)이 이미 맞춰져 있다. 그림판이나 외부 이미지 생성은 금지 — 재현 가능하고 텍스트로 diff 되어야 한다.
- 생성 스크립트는 **스크래치패드**에 두고 결과 `.svg`만 노트와 같은 폴더에 저장한다.
- **색만으로 구분하지 말고 라벨을 직접 붙인다** (색약 대응). 화살표 색과 화살촉 색을 맞춘다(`arrow(marker=...)` 생략 시 자동).

### 자주 깨지는 두 가지

- **SVG `<text>`는 연속 공백을 하나로 접는다.** 항목을 나열할 때 공백 여러 개로 띄우면 붙어 버린다. ` · ` 나 `   /   ` 같은 문자를 쓴다.
- **`band()`는 label을 `y+21`, sub를 `y+38`에 그린다.** 높이를 46보다 작게 주면 sub가 카드 밖으로 나간다.

만든 뒤 **반드시 눈으로 확인한다.**

```bash
python scripts/preview_svg.py "docs/<섹션>/<노트명>/<파일>.svg"
```

생성된 `*.preview.png`를 Read 도구로 열어 **라벨 겹침·잘림·어색한 배치**를 확인한다. 문제가 있으면 좌표를 고쳐 다시 렌더링한다. 자주 나오는 문제는 오른쪽 끝 라벨이 카드 밖으로 나가는 것과 트리 노드 라벨이 간선과 겹치는 것이다.

노트 본문에는 표준 마크다운으로 넣고 **바로 아래에 이탤릭 캡션 한 줄**을 붙인다.

```markdown
![무엇을 보여주는 그림인지](파일명.svg)

*그림이 말하는 결론 한 줄.*
```

## 4단계 — 등록

- `mkdocs.yml`의 `nav:`에 새 노트를 목차 순서대로 추가한다. 기존 항목의 순서·이름은 바꾸지 않는다.
- `docs/index.md`의 해당 섹션에서 텍스트 항목을 링크로 바꾼다. **표시 이름은 목차에 적힌 그대로 두고 경로만 하이픈 폴더명을 쓴다.**
  ```markdown
  - [탐색과 정렬](03-알고리즘/탐색-정렬/탐색-정렬.md)
  ```
- 새 최상위 섹션을 만드는 경우 번호는 기존 폴더와 겹치지 않게 다음 순번을 쓴다.

## 5단계 — 자동 검사

```bash
python scripts/check_notes.py <섹션>
```

16개 섹션 존재·들여쓰기·`답변 구조` 8항목·이미지 존재·SVG XML 유효성·nav/목차 등록을 한 번에 검사한다. **오류가 0이 될 때까지 고친다.** (경고는 판단해서 처리한다.)

```bash
python -m mkdocs build --strict
```

깨진 링크·이미지·nav 참조를 잡는다. 실패하면 고치고 다시 빌드한다.

## 6단계 — 실제 페이지 확인

도식을 추가했다면 로컬 서버를 띄워 **실제 렌더링**을 확인한다.

```bash
python -m mkdocs serve -a 127.0.0.1:8765
```

- `mkdocs.yml`의 `site_url` 때문에 **베이스 경로 `/Study-Note/`가 붙는다.** URL은 `http://127.0.0.1:8765/Study-Note/<섹션>/<노트명>/<노트명>/` 형태다 (한글 경로는 URL 인코딩된다). 서버 로그에 실제 주소가 찍히니 확인하고 쓴다.
- headless 브라우저로 스크린샷을 찍어 도식이 본문 폭에 맞게 들어가는지, 가로 스크롤이 생기지 않는지 본다. 창 높이를 충분히 크게(예: `1300x4200`) 잡아야 도식이 있는 아래쪽까지 찍힌다.
- 브라우저가 응답하지 않을 때를 대비해 타임아웃을 건다. **확인 후 서버는 반드시 종료한다.**

미리보기 PNG로 이미 확인했고 도식 폭이 780px 이하라면 이 단계는 건너뛰어도 된다. 건너뛰었다면 그 사실을 보고한다.

## 7단계 — 커밋 확인받기

1. 확인용 `*.preview.png`를 지운다.
   ```bash
   rm -f docs/<섹션>/*/*.preview.png
   ```
2. `git status`로 변경 파일을 확인하고, `site/`나 `.obsidian/`이 섞이지 않았는지 본다.
   **`c:\Work\Git` 자체의 git 상태와 혼동하지 않는다 — `Study Note`는 별도의 독립 저장소다.**
3. 개행문자(LF↔CRLF) 차이만 있는 파일이 `M`으로 뜨면 `git diff`로 확인하고 **커밋에서 제외한다** (`git add -A` 대신 경로를 지정해 add 한다).
4. 사용자에게 보고한다.
    - 추가·수정된 파일 목록과 노트별 라인 수
    - **2단계에서 찾은 사실 오류와 어떻게 고쳤는지** (가장 중요한 보고 항목이다)
    - 추가한 도식과 각각이 무엇을 보여주는지
    - 검사·빌드 통과 여부
5. **커밋/푸시 여부를 확인받는다. 확인 전에는 커밋도 푸시도 하지 않는다.**

승인 시 `Study Note` 디렉터리 안에서 실행한다. 커밋 메시지가 여러 줄이면 **파일로 넘긴다** — Bash 툴에 PowerShell here-string(`@'...'@`)을 쓰면 제목 줄이 깨진다.

```bash
git add docs/<섹션> docs/index.md mkdocs.yml
git commit -F <메시지파일>
```
